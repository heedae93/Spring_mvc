# 서블릿(Servlet) 학습 정리

> **이 문서의 목표**
> "서블릿이 무엇인지"를 개념부터 이해하고, 그 위에서 **우리가 실습으로 직접 짠 코드**가
> 왜 그렇게 생겼는지 파악한다.
>
> **미리 알아둘 것**: 실무(스프링 MVC)에서는 서블릿을 직접 만들 일이 거의 없다.
> 스프링이 `DispatcherServlet`이라는 서블릿을 이미 다 만들어두었기 때문이다.
> **여기서 서블릿을 직접 만들어 보는 이유는, 스프링 아래에서 실제로 무엇이 돌아가는지
> 그 "밑바닥 원리"를 이해하기 위한 학습 목적**이다. (2부의 코드는 전부 그런 학습용 코드다.)

---

# 1부. 개념편 — 서블릿이란 무엇인가

## 1. 서블릿(Servlet)이란?

**웹 요청(request)을 받아 처리하고, 응답(response)을 만들어 돌려주는 "프로그램 단위"** 이다.

브라우저가 서버에 요청을 보내면, 그 요청을 실제로 처리하는 자바 객체가 서블릿이다.
개념적으로 서블릿은 다음 역할만 담당한다.

```
요청이 들어온다 → (서블릿) 요청을 처리한다 → 응답을 만든다
```

핵심 성질:
- 서블릿의 **동작 방식·생명주기(언제 만들어지고 실행되고 사라지는지)는 이미 표준으로 정해져** 있다.
- 개발자는 그 틀 안에서 **"요청 하나를 어떻게 처리할지"라는 실제 로직만** 채운다.
- 즉 서블릿을 쓴다는 것은 **바퀴를 다시 발명하지 않고, 이미 정해진 규격 위에 로직만 얹는 것**이다.

> 자바에서 서블릿은 `HttpServlet` 클래스를 상속해서 만든다.
> `HttpServlet`을 상속받는 순간 그 클래스는 "하나의 서블릿"이 된다. (구체적인 코드는 2부에서)

---

## 2. 서블릿이 없다면? (서블릿이 편리한 이유)

브라우저가 요청 하나를 보냈을 때, 서블릿이 없다면 개발자가 이 모든 걸 직접 해야 한다.

| 해야 할 일 | 서블릿 없이 | 서블릿(WAS) 쓰면 |
|-----------|:---:|:---:|
| ① TCP 소켓 열기 / 연결 대기 | 직접 😫 | WAS가 대신 ✅ |
| ② 들어온 바이트 읽기 | 직접 😫 | WAS가 대신 ✅ |
| ③ HTTP 파싱 (경로/파라미터/헤더/본문/인코딩) | 직접 😫😫😫 | `request` 객체로 ✅ |
| ④ 라우팅 (어느 로직 실행할지) | if문 직접 | 매핑 자동 ✅ |
| ⑤ HTTP 응답 조립 (상태줄/헤더/본문) | 직접 😫 | `response` 객체로 ✅ |
| ⑥ 멀티스레드 관리 | 직접 😫😫 | WAS가 대신 ✅ |
| **내 비즈니스 로직** | 직접 | **직접 (이것만!)** |

→ 서블릿(WAS)은 **HTTP·네트워크·스레드라는 반복적이고 어려운 뼈대를 전부 대신 처리**해줘서,
개발자가 **`request`에서 값 꺼내기 → 로직 처리 → `response`에 쓰기**, 핵심에만 집중하게 해준다.

---

## 3. 서블릿 컨테이너 (WAS, 예: 톰캣)

**서블릿을 대신 실행하고 관리해주는 서버 프로그램.** 대표적으로 톰캣(Tomcat).

서블릿은 그냥 클래스일 뿐 혼자서는 아무것도 못 한다. 요청이 오면 컨테이너가:

1. 요청을 받는다 (네트워크/소켓 처리)
2. HTTP 메시지를 파싱해 `HttpServletRequest`를 만든다
3. 빈 `HttpServletResponse`를 만든다
4. URL에 매핑된 서블릿을 찾는다
5. 그 서블릿을 호출한다 ← **여기서 개발자가 짠 로직이 실행됨**
6. 응답 객체를 HTTP 메시지로 바꿔 브라우저에 보낸다

5번(내 로직)을 제외한 전부를 컨테이너가 대신 해준다.
또한 서블릿 객체를 개발자가 직접 `new` 하지 않는다 — **컨테이너가 만들고 생명주기를 관리**한다.

```
브라우저 ⇅ HTTP ⇅ 서블릿 컨테이너(톰캣) → 서블릿 / 또는 스프링의 DispatcherServlet
```

> 스프링 부트는 이 톰캣이 프로젝트 안에 **내장(embedded)** 되어 있어, 따로 설치 없이 main() 실행 시 함께 켜진다.

---

## 4. 서블릿은 싱글톤

톰캣은 서블릿을 요청마다 새로 만들지 않고, **처음에 딱 1개만 만들어 모든 요청이 공유**한다.

**이유**
- 요청마다 `new` 하면 낭비 → 하나 만들어 재사용하는 게 효율적 (성능/자원)
- 사용자별 데이터(예: `username=kim`)는 요청마다 새로 만들어지는 `request` 객체에 담기므로,
  서블릿 객체 자체는 공유해도 문제가 없다.

### ⚠️ 주의: 멤버 변수(공유 상태) 조심

여러 스레드가 같은 서블릿 1개를 동시에 실행하므로, **요청마다 값이 바뀌는 데이터를 멤버 변수에 담으면 안 된다.**

```java
private String username;   // ❌ 위험! 여러 스레드가 동시에 덮어써서 데이터가 섞임
```

- 컴파일 에러가 아니라, **동시 접속 시에만 조용히 데이터가 섞이는 버그(동시성 버그)** → 더 위험
- kim이 요청했는데 lee의 데이터를 받는 식의 사고 발생 가능
- 해결: 요청 관련 데이터는 **메서드 안의 지역 변수**로 둔다 (지역 변수는 스레드마다 독립)

| 멤버 변수 종류 | 안전? | 예시 |
|---|:---:|---|
| 요청마다 바뀌는 데이터 | ❌ | `username`, `count`, 로그인 사용자 |
| 초기화 후 안 바뀌는 상수/설정 | ✅ | `final String greeting` |
| 주입받은 stateless 객체 | ✅ | `memberService`, `repository` |

> 스프링 빈(`@Controller`, `@Service`)도 기본이 싱글톤이라 같은 원리·주의점이 적용된다.

## 5. 서블릿은 어떻게 동시 요청을 처리하나 (멀티스레드)

**연결고리**: 4번에서 "서블릿은 싱글톤(딱 1개)"이라고 했다. 그런데 사용자가 동시에 수백 명 들어오면,
그 1개짜리 서블릿이 어떻게 여러 요청을 동시에 처리할까? → **서블릿 컨테이너(톰캣)가 서블릿을
"멀티스레드"로 실행**하기 때문이다. 이게 4번의 "멤버 변수 주의"가 나온 근본 이유이기도 하다.

- 스레드 = 코드를 실행하는 "일꾼" 하나
- **톰캣은 요청마다 스레드를 하나씩 배정**해서, 그 스레드가 서블릿의 처리 메서드를 실행한다
  (싱글 스레드면 요청들이 서로 막혀서 하나 끝날 때까지 대기)
- 이 여러 스레드가 **같은 싱글톤 서블릿 1개**를 동시에 실행 → 그래서 멤버 변수 주의(4번)
- 즉 **"서블릿 하나 + 요청마다 스레드"** 구조. 서블릿을 이해하면 이 멀티스레드 얘기가 딸려 나온다.

### 스레드 풀 (Thread Pool)
스레드도 매번 만들면 비싸고, 폭주 시 서버가 죽는다. 그래서:
- 스레드를 미리 여러 개 만들어 풀에 대기
- 요청 오면 꺼내 쓰고, 끝나면 버리지 않고 풀에 반납(재사용)
- 개수 상한이 있어 폭주해도 서버 보호 (톰캣 기본 최대 200)

**이 모든 스레드 관리(생성/배정/반납)는 WAS가 대신 해준다. 개발자는 "요청 하나 처리 로직"만 짜면 된다.**
단, 그 로직을 스레드 안전하게 짜는 것(멤버 변수 주의)은 개발자 몫이다.

### 스레드 개수 설정
스레드 관리 "코드"는 안 짜지만, 개수 등 "설정값"은 개발자가 정할 수 있다.

```properties
# application.properties (스프링 부트 내장 톰캣)
server.tomcat.threads.max=200
server.tomcat.threads.min-spare=10
server.tomcat.max-connections=8192
server.tomcat.accept-count=100
```

### 적정 스레드 수 기준
- **CPU 바운드**(계산 위주): 스레드 ≈ 코어 수
- **I/O 바운드**(DB/API 대기 많음 = 웹 대부분): 코어 수보다 훨씬 많이 (대기 시간에 다른 스레드가 CPU 사용)
- 근사 공식: `코어 수 × (1 + 대기시간/작업시간)`
- **실제로는 부하 테스트(JMeter, nGrinder, k6)로 측정해 결정**. 이론값은 참고.

> **컨텍스트 스위칭 비용**: CPU가 실행 스레드를 바꿀 때 ① 이전 스레드 상태 저장/복원 ② CPU 캐시가 식어
> 느린 메모리 재접근이 발생. 그래서 스레드가 너무 많으면 오히려 느려진다.

## 6. 서블릿 애플리케이션의 배포 형태 (WAR vs JAR)

**연결고리**: 우리가 만든 서블릿은 3번에서 봤듯 **서블릿 컨테이너(톰캣) 위에서만** 돌아간다.
그럼 "내가 만든 서블릿들을 어떻게 묶어서 톰캣에 올려 실행하나?" → 이 **패키징(묶음) 형태**가 WAR/JAR이다.
특히 **WAR는 원래 서블릿/웹앱을 톰캣에 배포하기 위해 만들어진 전용 포맷**이라 서블릿과 직접 관련된다.

| 항목 | JAR | WAR |
|------|-----|-----|
| 뜻 | Java Archive | Web Application Archive |
| 용도 | 범용 자바 코드/라이브러리 | 웹 애플리케이션 전용 |
| 구조 | 자유 | `WEB-INF/` 등 정해진 구조 |
| 실행 | `java -jar`로 **단독 실행** | **WAS(톰캣)에 배포**해야 실행 |
| 톰캣 | (스프링 부트는) **내장** | 외부에 별도 설치 |
| 요즘 추세 | ✅ 주류 (스프링 부트) | 전통적/특수 상황 |

## 7. 우리가 배운 서블릿이 스프링에서 어떻게 쓰이나 (서블릿 vs 스프링 MVC)

**연결고리**: "그럼 실무에서 쓰는 스프링 MVC는 서블릿이랑 무슨 관계지?"에 대한 답이다.
결론부터: **스프링 MVC도 결국 서블릿 위에서 돈다.** 우리가 지금 배우는 서블릿이 바로 그 토대다.

"더 크다/작다"가 아니라 **계층(누가 누구 위에서 도는가)** 관계다.

```
┌─────────────────────────────────┐
│  스프링 MVC (@Controller, ...)    │  ← 서블릿 위에 지은 편의 기능
├─────────────────────────────────┤
│  서블릿 (HttpServlet, service)    │  ← 근본 토대 (자바 웹 표준)
├─────────────────────────────────┤
│  서블릿 컨테이너 (톰캣)            │  ← 실행·관리
└─────────────────────────────────┘
```

- **서블릿** = 자바 웹의 근본 토대(표준). 더 아래(기반)에 있다.
- **스프링 MVC** = 그 서블릿 위에 편의 기능을 잔뜩 얹은 프레임워크. 기능은 더 풍부.
- 스프링 MVC의 심장 **`DispatcherServlet`도 결국 `HttpServlet`을 상속한 서블릿**이다.
  (상속: `HttpServlet` → `HttpServletBean` → `FrameworkServlet` → `DispatcherServlet`)
- `DispatcherServlet`은 **모든 요청을 혼자 받아 알맞은 `@Controller`로 분배**하는 프론트 컨트롤러.

> 스프링 MVC를 "쓴다" = MVC라는 개념(패턴)을 스프링 팀이 구현해 배포한 **라이브러리**를
> 프로젝트에 의존성으로 추가해 가져다 쓴다는 뜻. (개념만 빌리는 게 아니라 실제 코드를 다운받아 씀)
>
> **다시 강조**: 그래서 실무에서는 서블릿을 직접 안 만든다. 2부의 코드는 이 토대를
> 눈으로 확인하기 위한 학습용이다.

# 2부. 실습 코드편 — 우리가 직접 만든 학습용 코드

> ⚠️ 아래 코드는 **스프링이 대신 해주는 밑바닥을 직접 체험하려고 만든 학습용 코드**다.
> 실무에서는 이렇게 `@WebServlet` + `service()`를 직접 짜지 않고, `@Controller`로 처리한다.

## 8. 왜 `@ServletComponentScan`을 붙였나?

```java
@ServletComponentScan   // 서블릿 자동 등록
@SpringBootApplication
public class ServletApplication {
    public static void main(String[] args) {
        SpringApplication.run(ServletApplication.class, args);
    }
}
```

### 두 종류의 애노테이션을 구분해야 한다

| | 애노테이션 | 누가 등록? | @ServletComponentScan 필요? |
|---|-----------|-----------|:---:|
| **스프링 빈** | `@Controller`, `@Service`, `@Component` | `@SpringBootApplication`이 자동 스캔 | ❌ |
| **표준 서블릿** | `@WebServlet`, `@WebFilter`, `@WebListener` | 기본으로는 스캔 안 함 | ✅ **필요** |

### 이유
- 스프링에 내장된 건 **`DispatcherServlet`** 이다. (자동 등록됨)
- 하지만 우리가 만들 `@WebServlet`은 **스프링 게 아니라 자바 서블릿 표준(javax.servlet)** 애노테이션이다.
- 전통적 외부 톰캣은 `@WebServlet`을 스캔해줬지만, **스프링 부트의 내장 톰캣은 기본적으로 스캔하지 않는다.**
- 그냥 두면 `@WebServlet("/hello")`를 붙여도 무시되어 `/hello`가 404.
- 그래서 `@ServletComponentScan`으로 **"@WebServlet/@WebFilter/@WebListener도 스캔해서 등록해줘"** 라고 켜준다.

→ `@Controller` 같은 스프링 자체 애노테이션엔 불필요하고, **우리처럼 순수 서블릿(`@WebServlet`)을 실습할 때만** 필요하다.

---

## 9. HelloServlet 코드 — 우리가 만든 학습용 서블릿

```java
@WebServlet(name = "helloServlet", urlPatterns = "/hello")
public class HelloServlet extends HttpServlet {

    @Override
    protected void service(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {

        System.out.println("HelloServlet.service");
        System.out.println("request = " + request);
        System.out.println("response = " + response);

        String username = request.getParameter("username");
        System.out.println("username = " + username);

        response.setContentType("text/plain");
        response.setCharacterEncoding("utf-8");
        response.getWriter().write("hello " + username);
    }
}
```

- `extends HttpServlet` → 이 클래스가 하나의 서블릿이 된다. (개념편 1번의 실제 구현)
- `@WebServlet(urlPatterns = "/hello")` → 이 서블릿을 `/hello` 주소에 매핑(등록). 8번의 `@ServletComponentScan`이 있어야 실제 등록됨.

### 참고: 왜 `doGet`이 아니라 `service()`를 오버라이드했나? (학습용 선택)

원래 `HttpServlet`의 `service()`는 HTTP 메서드(GET/POST)를 보고 알맞은 `doGet`/`doPost`로 나눠주는
**"교통정리 담당"** 으로 이미 구현되어 있다.

| 계층 | 메서드 | 구현 주체 |
|------|--------|-----------|
| 최상위 관문 | `service()` (Servlet 인터페이스) | 이미 구현됨 |
| HTTP 분기 | `service()` (HttpServlet) | **이미 구현됨** ← GET/POST 나눠줌 |
| 실제 처리 | `doGet()`, `doPost()` | 원래는 여기를 구현 |

그런데 이 코드는 부모 `service()`를 **통째로 덮어썼다**(`super.service()`도 호출 안 함).
- 그래서 GET/POST 분기가 사라지고, 메서드 상관없이 무조건 이 `service()` 하나로 들어온다.
- `doGet`, `doPost`는 호출되지 않는다.
- **의도된 학습용 선택**: "서블릿의 진짜 관문은 service()다"라는 동작 원리를 보여주려는 것.
  (실무/일반적으로는 `service()`가 아니라 `doGet`/`doPost`를 오버라이드한다.)

## 10. 코드 한 줄씩 상세 분석

### (1) HttpServletRequest를 어떻게 사용할 수 있나?

- 코드 어디에도 `new HttpServletRequest()`가 없다. **톰캣이 만들어서 매개변수로 넣어준다.** (개념편 3번)
- 흐름: `브라우저 요청 → 톰캣이 HTTP 파싱 → RequestFacade 객체 생성 → service(여기에 전달)`
- 우리는 받아서 **정보를 꺼내 쓰기만** 하면 된다.
  ```java
  request.getParameter("username");  // ?username=kim → "kim"
  request.getMethod();               // GET/POST
  request.getHeader("User-Agent");   // 헤더
  request.getRequestURI();           // 경로
  ```
- 실제 객체는 톰캣의 `RequestFacade`지만, 우리는 `HttpServletRequest`라는 **인터페이스(규격)** 로 받는다.
  → 톰캣이든 다른 WAS든 코드가 안 바뀐다.

> 실행 로그로 확인됨:
> `request = org.apache.catalina.connector.RequestFacade@74bea4a0`
> - `org.apache.catalina...` = 톰캣(Catalina)이 만든 클래스
> - `RequestFacade` = HttpServletRequest 인터페이스의 실제 구현체
> - `@74bea4a0` = 객체 식별용 해시코드 (의미 없음, 무시)
> - **Facade** = 톰캣 내부의 복잡한 진짜 객체를 감추고, 안전한 메서드만 열어주는 "껍데기" 패턴

### (2) return이 없는데 어떻게 응답이 클라이언트로 날아가나?

**핵심: 응답은 return으로 돌려주는 게 아니라, response 객체에 "써넣는" 방식이다.**

```
① 톰캣이 "빈 response 객체"를 만들어 service()에 넣어줌 (빈 답안지)
② 나는 response에 내용을 써넣음
   - setContentType / setCharacterEncoding → 헤더 기록
   - getWriter().write(...)                → 본문 기록
③ service() 메서드가 끝남 (return 없어도 메서드 끝나면 종료)
④ 톰캣이 그 response를 보고 HTTP 응답 메시지로 조립 → 브라우저로 전송
```

- 내가 응답을 "보내는" 게 아니라, response에 **채워만 놓으면 톰캣이 대신 보낸다.**
- 그래서 `service()`는 `void`여도 되고, `return`이 없어도 응답이 나간다 (데이터는 이미 response 안에 있음).
- 비유: 회사가 준 양식(response)에 내용만 채워 제출하면 발송은 회사(톰캣)가 대신.

> 스프링 MVC의 `@Controller`는 `return "뷰이름"`을 쓰지만, 그 내부에서도 결국 이 response에
> 써넣는 작업이 일어난다. 밑바닥 원리는 동일.

### (3) Content-Type: `text/plain` — 앞/뒤 의미

```java
response.setContentType("text/plain");
```

- 응답 본문이 **어떤 종류의 데이터인지** 브라우저에 알려주는 값 (= MIME 타입)
- 형식: `타입/서브타입`
  - 앞(`text`) = 대분류 ("텍스트 계열이야")
  - 뒤(`plain`) = 세부 종류 ("서식 없는 순수 텍스트야")

| Content-Type | 의미 |
|--------------|------|
| `text/plain` | 순수 텍스트 (글자 그대로 표시) |
| `text/html` | HTML 문서 (브라우저가 웹페이지로 렌더링) |
| `application/json` | JSON 데이터 |
| `image/png` | PNG 이미지 |

- **왜 지정?** 브라우저는 Content-Type을 보고 처리 방식을 결정한다.
  같은 `<h1>hi</h1>`도 `text/plain`이면 태그까지 글자로 보이고, `text/html`이면 큰 제목으로 렌더링된다.

### (4) 인코딩 / UTF-8 / 왜 지정하나

```java
response.setCharacterEncoding("utf-8");
```

**인코딩이란?**
- 컴퓨터는 글자를 모르고 숫자(0/1)만 안다. 그래서 **글자 → 숫자(바이트)로 바꾸는 규칙**이 인코딩.
- 규칙이 여러 종류라, 같은 글자도 규칙마다 다른 숫자가 된다.
  - `'가'` → UTF-8: `234 176 128` / EUC-KR: `176 161`

**왜 지정하나? (글자 깨짐 방지)**
- 보내는 쪽(서버)과 받는 쪽(브라우저)이 **같은 규칙**을 써야 글자가 복원된다.
- 규칙 불일치 = 한글 깨짐(`ê°€`, `?????`, `�`)의 원인.
- `setCharacterEncoding("utf-8")` = "나는 UTF-8로 글자를 숫자로 바꿔 보낼게, 너도 UTF-8로 읽어".

**UTF-8이란?**
- 전 세계 모든 문자(한글/영어/한자/이모지)를 표현하는 인코딩 규칙.
- 웹 표준이자 사실상 기본값. 영어 1바이트, 한글 3바이트 식으로 필요한 만큼 사용(효율적).
- 특별한 이유 없으면 **무조건 UTF-8**이 정답.

**둘의 관계**
```java
response.setContentType("text/plain");   // 데이터 종류
response.setCharacterEncoding("utf-8");  // 글자 인코딩
```
→ 실제 응답 헤더: `Content-Type: text/plain;charset=utf-8`
(`response.setContentType("text/plain;charset=utf-8")`로 한 줄로 합쳐 쓰기도 함)

### (5) 한눈 정리

| 코드 | 하는 일 |
|------|---------|
| `HttpServletRequest request` | 톰캣이 만들어 넣어준 요청 정보 객체 (내가 new 안 함) |
| `request.getParameter("username")` | `?username=kim`에서 `kim` 꺼내기 |
| `HttpServletResponse response` | 톰캣이 만들어 넣어준 빈 응답 객체 (여기에 채워 넣음) |
| `response.setContentType("text/plain")` | "본문은 순수 텍스트" (타입/서브타입) |
| `response.setCharacterEncoding("utf-8")` | "글자는 UTF-8 인코딩" (깨짐 방지) |
| `response.getWriter().write(...)` | 응답 본문에 내용 써넣기 |
| **return 없음** | response에 채워두면 톰캣이 알아서 HTTP 응답으로 조립·전송 |

## 11. RequestHeaderServlet — HTTP 요청 정보 전체 조회

> `HelloServlet`에서는 `request.getParameter()` 하나만 썼다. 이번엔 **`request` 객체가 제공하는
> 다양한 조회 메서드**로, HTTP 요청 안에 담긴 정보(시작 줄·헤더·연결 정보)를 전부 꺼내보는 실습이다.

### 예제가 의미하는 것
브라우저가 `http://localhost:8080/request-header`로 접속하면, 이 서블릿은 요청에 담긴 모든 정보를
**콘솔에 출력**한다. (응답 화면은 비어 있고, 결과는 IntelliJ 하단 콘솔에서 확인)
→ "요청(request) 안에는 대체 뭐가 들어있나?"를 눈으로 보는 게 목적.

### 먼저: HTTP 요청 메시지의 구조
```
GET /request-header?username=kim HTTP/1.1     ← ① 시작 줄 (start-line)
Host: localhost:8080                          ┐
User-Agent: Mozilla/5.0                       │ ② 헤더 (headers)
Accept-Language: ko-KR,ko;q=0.9               │
Cookie: sessionId=abc123                      ┘
                                              ← 빈 줄 (헤더 끝)
{ "name": "kim" }                             ← ③ 본문 (body, POST 등)
```
톰캣이 이 메시지를 파싱해 `request` 객체에 담아주므로, 우리는 메서드만 호출하면 된다.

### 코드 구조
```java
protected void service(...) {
    printStartLine(request);    // ① 시작 줄 조회
    printHeaders(request);      // ② 모든 헤더 조회
    printHeaderUtils(request);  // ② 자주 쓰는 헤더 "편의 조회"
    printEtc(request);          // 기타(연결 정보) 조회
}
```

### ① printStartLine — 시작 줄 정보
```java
request.getMethod()       // GET, POST 등 HTTP 메서드
request.getProtocol()     // HTTP/1.1
request.getScheme()       // http / https
request.getRequestURL()   // http://localhost:8080/request-header (호스트 포함 전체 주소)
request.getRequestURI()   // /request-header (경로만)
request.getQueryString()  // username=kim (? 뒤의 쿼리)
request.isSecure()        // https 여부
```
- **URL vs URI**: `getRequestURL()`=전체 주소, `getRequestURI()`=경로만, 쿼리는 `getQueryString()`으로 따로.

### ② printHeaders — 모든 헤더 반복 조회
```java
request.getHeaderNames().asIterator()
        .forEachRemaining(headerName -> System.out.println(headerName + ": " + request.getHeader(headerName)));
```
- `getHeaderNames()` → 요청에 온 **모든 헤더 이름 목록** 반환 (구식 타입인 `Enumeration`)
- `.asIterator()` (자바 9+) → 요즘 스타일로 순회할 수 있게 변환 → `forEachRemaining`으로 하나씩 출력
- `getHeader(headerName)` → 그 이름에 해당하는 **헤더 값**을 조회
  - 즉 `getHeaderNames()`(이름 목록)로 돌면서, 각 이름을 `getHeader()`에 넣어 값을 꺼내 `이름: 값`으로 출력

**출력 예시**
```
host: localhost:8080
connection: keep-alive
user-agent: Mozilla/5.0 ...
accept-language: ko-KR,ko;q=0.9,en-US;q=0.8
```

> 💡 흔한 실수: 뒤쪽에 값 대신 `headerName`을 또 쓰면 `host: host`처럼 **이름만 두 번** 나온다.
> 값을 보려면 반드시 `request.getHeader(headerName)`로 값을 조회해야 한다.

### ③ printHeaderUtils — 자주 쓰는 헤더 편의 조회
헤더를 매번 `getHeader("이름")`으로 꺼내면 번거로우니, 서블릿이 자주 쓰는 것들에 **전용 메서드**를 제공한다.
```java
request.getServerName() / getServerPort()   // Host 헤더 → 서버 이름/포트
request.getLocales() / getLocale()          // Accept-Language 헤더 → 선호 언어(우선순위/1순위)
request.getCookies()                        // Cookie 헤더 → Cookie[] (null 체크 필수!)
request.getContentType() / getContentLength() / getCharacterEncoding()  // 본문 관련
```
- 이것들도 결국 다 헤더다. `getServerName()`은 `Host` 헤더를 파싱해주는 것뿐. 직접 `getHeader("Host")` 해도 되지만 편의 메서드가 더 안전.
- `getCookies()`는 쿠키가 없으면 `null` → 그냥 for로 돌리면 NPE. 그래서 `if (... != null)`로 감쌌다.

### ④ printEtc — 기타(네트워크 연결 정보)
HTTP 메시지 내용이 아니라, **누가 어디서 접속했는지(TCP 연결 정보)**.
```java
// Remote = 요청 보낸 쪽 (클라이언트)
request.getRemoteHost() / getRemoteAddr() / getRemotePort()
// Local = 요청 받은 쪽 (내 서버)
request.getLocalName() / getLocalAddr() / getLocalPort()
```
- **Remote = 상대방(클라이언트), Local = 나(서버)** 로 기억하면 안 헷갈림.

### 사용된 개념 정리
| 개념 | 설명 |
|------|------|
| HTTP 요청 구조 | 시작 줄 / 헤더 / 본문 3부분 |
| `request` 조회 메서드 | 톰캣이 파싱해 담아둔 요청 정보를 꺼내는 다양한 메서드 |
| `Enumeration` + `asIterator()` | 구식 컬렉션(Enumeration)을 자바 9+ 스타일로 순회 |
| 편의 메서드 | 자주 쓰는 헤더(Host, Language, Cookie, Content)를 전용 메서드로 제공 |
| null 체크 | `getCookies()`는 null 가능 → NPE 방지 |
| Remote vs Local | 클라이언트 정보 vs 서버 정보 |

## 12. IntelliJ 메서드 추출 단축키 (Extract Method)

`printStartLine`, `printHeaders` 같은 메서드들은 **원래 `service()` 안에 한 덩어리로 들어있던 코드**였다.
그걸 **"메서드 추출(Extract Method)"** 기능으로 각각의 메서드로 분리한 것이다.

### 무엇인가
길고 복잡한 코드 블록을 **드래그로 선택 → 단축키 → 별도 메서드로 자동 분리**해주는 리팩터링 기능.
- 선택한 코드가 새 메서드로 빠지고
- 원래 자리에는 그 메서드 **호출문**이 자동으로 들어가며
- 필요한 변수(예: `request`)는 **매개변수로 자동 전달**된다

### 단축키
| OS | 단축키 |
|----|--------|
| **Windows / Linux** | `Ctrl + Alt + M` |
| **macOS** | `Cmd + Option + M` |

### 사용법
1. 메서드로 빼고 싶은 코드 줄들을 **드래그로 선택**
2. 단축키를 누름 → **Windows/Linux: `Ctrl + Alt + M`** / **macOS: `Cmd + Option + M`**
3. 뜨는 창에서 **메서드 이름 입력**(예: `printStartLine`) → Enter
4. 끝. 코드가 새 메서드로 분리되고 원래 자리엔 호출문이 생김

### 왜 쓰나
- `service()`가 수십 줄로 길어지면 읽기 어렵다 → **역할 단위로 쪼개면** 한눈에 흐름이 보인다
  (`service()`만 보면 "시작줄 → 헤더 → 편의조회 → 기타" 순서가 딱 드러남)
- 코드 중복 제거, 재사용에도 유용

**함께 알아두면 좋은 리팩터링 단축키 (IntelliJ)**

| 기능 | Windows / Linux | macOS | 설명 |
|------|-----------------|-------|------|
| 메서드 추출 | `Ctrl + Alt + M` | `Cmd + Option + M` | 코드 → 메서드로 분리 |
| 변수 추출 | `Ctrl + Alt + V` | `Cmd + Option + V` | 값/식 → 변수로 분리 |
| 이름 바꾸기 | `Shift + F6` | `Shift + F6` | 변수/메서드명 일괄 변경(참조까지 자동) |
| 인라인(추출 반대) | `Ctrl + Alt + N` | `Cmd + Option + N` | 메서드/변수를 원래 자리로 되돌림 |
| 리팩터링 메뉴 전체 | `Ctrl + Alt + Shift + T` | `Ctrl + T` | 가능한 리팩터링 목록 표시 |

## 13. 잠깐, 큰 그림부터 — "클라이언트는 서버에 데이터를 어떻게 보내는가?"

자, 여기서부터 강의의 결이 한 번 바뀝니다. 지금까지(9~11번)는 "요청이 들어왔을 때 그 안을 **들여다보는**"
연습이었어요. `request` 객체에서 헤더 꺼내고, 시작 줄 읽고. 그런데 실제 웹 서비스는 사용자가 **값을 보내야**
돌아갑니다. 로그인하려면 아이디·비밀번호를 보내야 하고, 검색하려면 검색어를 보내야죠.

그래서 질문을 하나 던지고 시작하겠습니다. **"클라이언트가 서버로 데이터를 보내는 방법이 몇 가지나 될까요?"**

놀랍게도 딱 **3가지**입니다. 이게 전부예요. 이 3가지만 머릿속에 지도로 그려두면, 앞으로 스프링에서
`@RequestParam`을 쓸지 `@RequestBody`를 쓸지 평생 안 헷갈립니다. 반대로 이걸 안 잡고 넘어가면
계속 "이건 왜 값이 null로 오지?" 하면서 삽질하게 돼요. 그러니 여기 꼭 시간을 들입시다.

| | 방법 | 데이터가 **어디에** 실리나 | 형식 | 대표 상황 |
|---|------|:---:|------|---------|
| **①** | GET 쿼리 파라미터 | URL 뒤 `?key=value` | `key=value&...` | 검색·필터·페이징 (조회) |
| **②** | POST HTML Form | 메시지 **바디** | `application/x-www-form-urlencoded` | 회원가입 폼 제출 |
| **③** | HTTP message body | 메시지 **바디** | 순수 텍스트 / **JSON** / XML | HTTP API (앱·Ajax·서버 간) |

이 표에서 제가 진짜 강조하고 싶은 한 가지는 이겁니다. **①과 ②를 "위치가 다르니 다른 거겠지"라고
생각하기 쉬운데, 서버 입장에서는 사실상 같은 것**이에요. 왜냐하면 둘 다 데이터 모양이 `username=hello&age=20`이라는
**똑같은 `key=value` 형식**이거든요. 하나는 URL에 붙어 있고 하나는 바디에 들어있을 뿐. 그래서 뒤에서 보겠지만
**서블릿 코드가 글자 하나 안 바뀝니다.** 이게 핵심 포인트예요.

반면 **③은 결이 다릅니다.** 바디에 `key=value`가 아니라 `{"username":"hello"}` 같은 JSON 덩어리나 순수 텍스트가
통째로 들어와요. 그래서 `getParameter()` 같은 걸로는 절대 못 꺼내고, **바디를 직접 읽어야** 합니다.

한 장의 그림으로 이 3가지가 실제 HTTP 메시지에서 어떻게 다른지 보여드릴게요. **위치의 차이**를 눈으로 익혀두세요.

```
①  GET 쿼리        GET /request-param?username=hello&age=20  HTTP/1.1   ← 값이 URL에!
                   (바디 없음)

②  POST Form       POST /request-param  HTTP/1.1
                   content-type: application/x-www-form-urlencoded
                                                                        ← 빈 줄(헤더 끝)
                   username=hello&age=20                                ← 값이 바디에 (key=value)

③  message body    POST /request-body-json  HTTP/1.1
                   content-type: application/json
                                                                        ← 빈 줄(헤더 끝)
                   {"username":"hello", "age":20}                       ← 값이 바디에 (JSON 덩어리)
```

②와 ③은 둘 다 "바디"에 값을 싣지만, **content-type이 다르다**는 걸 봐두세요. ②는 `x-www-form-urlencoded`,
③은 `application/json`. 서버는 이 content-type을 보고 "아 이건 폼 데이터구나 / JSON이구나"를 판단합니다.
그래서 content-type은 그냥 장식이 아니라 **바디를 어떻게 해석할지 알려주는 이정표**예요.

이제 이 3가지를 하나씩 코드로 만져봅시다. 순서는 ①②를 묶어서(14번), ③을 텍스트(15번) → JSON(16번)으로 갑니다.

## 14. ① GET 쿼리 & ② POST Form — "출처는 달라도 꺼내는 법은 똑같다" (RequestParamServlet)

방금 13번에서 "①과 ②는 서버 입장에선 같은 것"이라고 했죠. 그 말을 코드로 증명하는 시간입니다.
결론을 먼저 못 박고 갈게요: **GET 쿼리로 오든 POST 폼으로 오든, 서블릿은 `request.getParameter()` 하나로 똑같이 꺼냅니다.**

### 왜 같은 코드로 처리될까? (여기가 이해의 핵심)
- **GET 쿼리 파라미터**는 `.../request-param?username=hello&age=20`처럼 URL 꼬리에 붙어 옵니다.
- **POST HTML Form**은 바디에 `username=hello&age=20`이 실려 오고, content-type이 `application/x-www-form-urlencoded`죠.
- 그런데 톰캣이 이 둘을 파싱해서 `request`에 담을 때, **"URL에서 왔든 폼 바디에서 왔든 그냥 파라미터"** 로 똑같이 취급합니다.
- 그래서 우리는 출처를 신경 쓸 필요 없이 `getParameter("username")` 하면 됩니다.
  이걸 통틀어 **"요청 파라미터(request parameter) 조회"** 라고 불러요.

> 💬 이게 왜 좋냐면요 — 화면을 GET 링크로 만들다가 나중에 "보안상 폼(POST)으로 바꾸자"가 되어도
> **서버 코드는 그대로**입니다. 껍데기(요청 방식)만 바뀌고 알맹이(파라미터 조회)는 안 바뀌니까요.

### 코드 — RequestParamServlet
```java
@WebServlet(name = "requestParamServlet", urlPatterns = "/request-param")
public class RequestParamServlet extends HttpServlet {

    @Override
    protected void service(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {

        // (1) 전체 파라미터를 한 바퀴 돌며 이름=값 출력
        System.out.println("[전체 파라미터 조회] - start");
        request.getParameterNames().asIterator()
                .forEachRemaining(paramName ->
                        System.out.println(paramName + "=" + request.getParameter(paramName)));
        System.out.println("[전체 파라미터 조회] - end");

        // (2) 이름을 콕 집어 하나씩 (실무에서 제일 많이 쓰는 방식)
        System.out.println("[단일 파라미터 조회]");
        String username = request.getParameter("username");   // ?username=hello → "hello"
        String age = request.getParameter("age");
        System.out.println("username = " + username);
        System.out.println("age = " + age);

        // (3) 같은 이름이 여러 개 올 때 (예: 체크박스)
        System.out.println("[이름이 같은 복수 파라미터 조회]");
        String[] usernames = request.getParameterValues("username");
        for (String name : usernames) {
            System.out.println("username = " + name);
        }

        response.getWriter().write("ok");
    }
}
```

11번의 `RequestHeaderServlet` 기억나시죠? 거기서 헤더 이름을 `getHeaderNames()`로 순회했잖아요.
여기 (1)의 `getParameterNames().asIterator()...`는 **완전히 똑같은 패턴**입니다. "이름 목록을 받아서
하나씩 돌면서 값을 꺼낸다." 서블릿 API가 이런 식으로 일관되게 설계돼 있어요. 한 번 익히면 계속 재활용됩니다.

### 파라미터 조회 메서드 4종 — 상황별로 골라 쓰기
| 메서드 | 반환 | 언제 쓰나 |
|--------|------|-----------|
| `getParameter("username")` | `String` 하나 | 이름이 유일할 때 — **90%는 이거** |
| `getParameterNames()` | 이름 목록(`Enumeration`) | 전체 이름을 훑을 때 |
| `getParameterMap()` | `Map<String, String[]>` | 전체를 Map으로 통째로 |
| `getParameterValues("username")` | `String[]` | **같은 이름**이 여러 개일 때 (체크박스 등) |

### ⚠️ 여기서 신입이 꼭 한 번은 밟는 지뢰 두 개
1. **중복 이름에 `getParameter()`를 쓰면 값이 잘린다.**
   `?username=hello&username=kim`처럼 같은 이름이 둘인데 `getParameter("username")`을 하면 **맨 앞 하나(`hello`)만**
   돌려줍니다. `kim`은 조용히 사라져요. 여러 개가 올 수 있으면 반드시 `getParameterValues()`를 쓰세요.
2. **없는 파라미터는 `null`이다.** 위 코드의 `getParameterValues("username")`도, 만약 username을 아예 안 보내면
   `null`이 옵니다. 그 상태로 `for`문을 돌리면 곧장 `NullPointerException`이에요. 실무에선 조회 전에 null 체크가 필수입니다.
   (지금 예제 코드는 "값이 온다"고 가정한 학습용이라 체크를 생략한 것뿐)

### POST Form도 정말 같은 코드로 되는지 — hello-form.html로 직접 확인
```html
<form action="/request-param" method="post">
    username: <input type="text" name="username" />
    age:      <input type="text" name="age" />
    <button type="submit">전송</button>
</form>
```
이 폼에서 `전송`을 누르면 브라우저가 알아서 **content-type을 `application/x-www-form-urlencoded`로 붙이고**
바디에 `username=...&age=...`를 담아 POST로 쏩니다. 그런데 받는 쪽 `RequestParamServlet`은?
**아까 GET으로 접속했을 때 돌린 그 코드 그대로** 값을 꺼냅니다. 코드를 한 줄도 안 고쳤는데 둘 다 동작해요.
이 순간을 눈으로 보는 게 이 실습의 진짜 목적입니다. — "아, 정말 출처가 안 중요하구나."

> 💡 content-type 정리: **GET 쿼리만** 보낼 땐 바디를 안 쓰니 content-type이 **아예 없습니다.**
> **POST 폼**은 바디를 쓰니 `application/x-www-form-urlencoded`가 반드시 붙고요. 이 차이도 개발자 도구(Network 탭)에서 직접 확인해보세요.

## 15. ③ 바디 직접 읽기 — 단순 텍스트 (RequestBodyStringServlet)

이제 13번의 세 번째 방법, **HTTP message body**로 넘어갑니다. 여기서 사고방식을 한 번 바꿔야 해요.

앞의 14번까지는 "톰캣이 파싱해서 `getParameter()`로 예쁘게 꺼내주는" 세계였습니다. 그런데 HTTP API에서는
클라이언트가 바디에 `key=value`가 아니라 **그냥 텍스트나 JSON을 통째로** 던집니다. 톰캣은 이걸 파라미터로
파싱하지 않아요 — content-type이 폼도 아니고, 정해진 형식이 없으니까요. 그래서 **우리가 바디를 직접 읽어야** 합니다.

### 코드 — RequestBodyStringServlet
```java
@WebServlet(name = "requestBodyStringServlet", urlPatterns = "/request-body-string")
public class RequestBodyStringServlet extends HttpServlet {

    @Override
    protected void service(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {

        ServletInputStream inputStream = request.getInputStream();  // 바디를 "바이트 흐름"으로 연다
        String messageBody = StreamUtils.copyToString(inputStream, StandardCharsets.UTF_8);  // 바이트 → 문자열

        System.out.println("messageBody = " + messageBody);

        response.getWriter().write("ok");
    }
}
```

딱 두 줄이지만, 두 줄 다 곱씹을 가치가 있습니다.

### `request.getInputStream()` — 왜 "스트림"일까?
바디는 크기가 얼마나 될지 몰라요. 짧은 한 줄일 수도, 수 MB짜리 파일일 수도 있죠. 그래서 서블릿은 바디를
"한 방에 String으로 주는" 대신 **`InputStream`(바이트가 흘러나오는 수도꼭지)** 로 줍니다. 필요한 만큼
읽어가라는 뜻이에요. 그리고 여기서 나오는 건 문자가 아니라 **바이트(byte)** 라는 점이 중요합니다.

### 바이트를 문자로 바꾸려면? → 인코딩이 다시 등장
4번(개념편)에서 인코딩 얘기했던 거 기억나시죠? "컴퓨터는 글자를 모르고 숫자만 안다." 바로 그 이야기가
여기서 실전으로 돌아옵니다. `InputStream`에서 나온 바이트 뭉치(`234 176 128`...)를 사람이 읽는 `"가"`로
되돌리려면 **어떤 규칙으로 해석할지(UTF-8)** 를 반드시 알려줘야 해요. 안 그러면 한글이 `ê°€`로 깨집니다.

- `StreamUtils.copyToString(inputStream, StandardCharsets.UTF_8)`
  → 원래는 스트림에서 바이트를 `while` 루프로 조금씩 읽어 버퍼에 모으고 문자로 변환하는… 꽤 귀찮은 코드예요.
  스프링이 주는 이 `StreamUtils` 유틸이 그 과정을 **한 줄로** 대신해줍니다. (스프링이 없으면 직접 짜야 함)

> 💬 핵심 대비: **파라미터는 `getParameter()`, 바디는 `getInputStream()`.** 이 둘을 섞어 쓰면 값이 안 나옵니다.
> "바디에 JSON을 보냈는데 `getParameter("username")`이 null이에요" — 이게 초보의 단골 질문인데, 당연합니다.
> JSON은 파라미터가 아니거든요. 반드시 바디를 읽어야 해요.

### 🤔 심화 — "그럼 POST Form 데이터는 바디에 있는데, 왜 `getInputStream`이 아니라 `getParameter`로 꺼냈지?"

14번에서 "GET 쿼리든 POST Form이든 똑같이 `getParameter()`로 꺼낸다"고 했죠. 그런데 잘 생각해보면 이상합니다.
**POST Form 데이터도 엄연히 바디에 들어있잖아요?** 그럼 form도 이 15번처럼 `getInputStream()`으로 읽어야 하는 거 아닌가?

정답부터: **form 데이터도 `getInputStream()`으로 읽을 수 있습니다.** 못 쓰는 게 아니에요. form이 바디에 있으니 당연히 가능합니다.
다만 읽으면 **날것의 문자열** `username=hello&age=20`이 그대로 나와서, `&`와 `=`로 **직접 잘라 파싱해야** 합니다. 귀찮으니까 안 쓸 뿐이죠.

그럼 왜 form은 `getParameter()`가 되고, 이 15번의 텍스트나 16번의 JSON은 안 될까? → **content-type 차이** 때문입니다. 이게 핵심입니다.

| 바디 내용 | content-type | 톰캣이 바디를 **자동 파싱**? | `getParameter()` | `getInputStream()` |
|-----------|--------------|:---:|:---:|:---:|
| POST Form | `application/x-www-form-urlencoded` | ✅ 한다 | ✅ 됨 (편함) | ✅ 됨 (날것, 직접 파싱) |
| 순수 텍스트 | `text/plain` 등 | ❌ 안 한다 | ❌ 안 됨 | ✅ 이것만 |
| JSON | `application/json` | ❌ 안 한다 | ❌ 안 됨 | ✅ 이것만 |

- 톰캣은 content-type이 **`x-www-form-urlencoded`일 때만** "이건 `key=value` 폼이구나" 하고 **바디를 자동 파싱해 파라미터로** 만들어 줍니다.
  그래서 form은 `getParameter()`가 되는 거예요. GET 쿼리와 통일되는 것도 이 자동 파싱 덕분이고요.
- 텍스트·JSON은 content-type이 폼이 아니라서 톰캣이 "내가 파싱할 규격이 아니네" 하고 **바디를 그냥 놔둡니다.** → `getParameter()`는 null, `getInputStream()`으로 직접 읽는 수밖에 없어요.

> 즉 **form이 특별해서 `getParameter()`가 되는 게 아니라, "톰캣이 자동 파싱해주는 형식"이라서** 되는 것.

### ⚠️ 그리고 둘을 **동시에는 못 쓴다**
`getParameter()`와 `getInputStream()`을 **한 요청에서 둘 다** 쓰려 하면 안 됩니다. **바디는 스트림이라 한 번 읽으면 비워지기** 때문이에요.
- `getParameter()`를 먼저 호출 → 톰캣이 바디를 읽어 파싱해버림 → 이후 `getInputStream()`은 **텅 빈** 스트림
- `getInputStream()`을 먼저 읽음 → 바디 소진 → 이후 (바디의) `getParameter()`는 **null**

→ 그래서 실무에선 **form이면 `getParameter()` 하나로**, **텍스트·JSON이면 `getInputStream()` 하나로** — 둘 중 하나만 씁니다.

#### 🌊 "한 번 읽으면 비워진다"가 무슨 뜻? — 스트림은 흘러가는 물줄기
`InputStream`은 이름 그대로 **흐르는 물줄기**입니다. 배열·문자열처럼 어딘가 저장돼 있어 몇 번이고 다시 보는 게 아니에요.
- **배열/문자열** = 책 📖 → 몇 번이든 다시 펼쳐 읽을 수 있음
- **스트림** = 수도꼭지 물 💧 → **한 번 흘려보내면 그 물은 사라짐.** 다시 틀어도 *아까 그 물*은 안 나옴

바디는 네트워크를 타고 서버로 **한 번 흘러들어오는 데이터**라, 읽는 순간 읽기 위치(커서)가 끝(EOF)까지 이동합니다. 그래서 두 번째로 읽으려 하면 남은 게 없어 빈 값이 나와요.

```java
ServletInputStream inputStream = request.getInputStream();

String body1 = StreamUtils.copyToString(inputStream, StandardCharsets.UTF_8);
System.out.println(body1);   // "username=hello&age=20"  ✅ 잘 나옴 (물줄기를 끝까지 다 마심)

String body2 = StreamUtils.copyToString(inputStream, StandardCharsets.UTF_8);
System.out.println(body2);   // ""  ← 텅 빔! ❌ (이미 다 흘러가버려서 읽을 게 없음)
```

그리고 앞에서 말한 **form의 "자동 파싱"이라는 것도 결국 톰캣이 대신 바디 스트림을 끝까지 읽어** `key=value`를 잘라내는 작업이에요. 그러니 `getParameter()`(=톰캣이 스트림 읽기)와 내 `getInputStream()`(=내가 스트림 읽기)은 **같은 하나의 물줄기를 놓고 다투는 셈** — 먼저 마신 쪽이 다 마셔버립니다. 이게 "동시에 못 쓴다"의 진짜 이유입니다.

> 💡 참고: 바디를 꼭 여러 번 읽어야 하는 특수한 경우엔 처음 읽을 때 내용을 따로 저장해 재사용하게 해주는 `ContentCachingRequestWrapper` 같은 장치를 씁니다. 기본 스트림 자체는 **"1회성"** 이 원칙 — 지금은 이것만 기억하면 충분합니다.

## 16. ③ 바디 직접 읽기 — JSON (RequestBodyJsonServlet)

15번에서 바디를 문자열로 읽는 법을 배웠습니다. 그런데 실무 HTTP API가 실제로 주고받는 건 대부분 순수 텍스트가
아니라 **JSON**이에요. 그럼 15번과 뭐가 다를까요? 딱 **한 단계**가 더 붙습니다: **문자열을 객체로 바꾸기(파싱).**

### 먼저 그릇을 준비 — HelloData
```java
@Getter @Setter
public class HelloData {
    private String username;
    private int age;
}
```
JSON `{"username":"kim","age":20}`을 받아 담을 **자바 객체**입니다. 규칙은 하나예요 — **JSON의 키 이름과
자바 필드 이름을 맞춘다**(`username`, `age`). `@Getter @Setter`(Lombok)로 getter/setter를 자동 생성하는데,
이게 있어야 JSON 라이브러리가 setter로 값을 밀어 넣을 수 있습니다.

### 코드 — RequestBodyJsonServlet
```java
@WebServlet(name = "requestBodyJsonServlet", urlPatterns = "/request-body-json")
public class RequestBodyJsonServlet extends HttpServlet {

    private ObjectMapper objectMapper = new ObjectMapper();   // JSON ↔ 객체 변환기

    @Override
    protected void service(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {

        // ① 여기까지는 15번과 완전히 똑같다 — 바디를 문자열로 읽기
        ServletInputStream inputStream = request.getInputStream();
        String messageBody = StreamUtils.copyToString(inputStream, StandardCharsets.UTF_8);
        System.out.println("messageBody = " + messageBody);   // {"username":"kim","age":20}

        // ② 여기가 새로 추가된 한 단계 — 문자열(JSON)을 객체로 변환
        HelloData helloData = objectMapper.readValue(messageBody, HelloData.class);

        System.out.println("helloData.username = " + helloData.getUsername());  // kim
        System.out.println("helloData.age = " + helloData.getAge());            // 20

        response.getWriter().write("ok");
    }
}
```

### 15번과 딱 하나 다른 점 = "② 파싱" 한 줄
①번 블록은 15번과 글자까지 똑같아요. 새로 생긴 건 ②의 `objectMapper.readValue(messageBody, HelloData.class)`
한 줄뿐입니다. 이 줄이 하는 일은: **`{"username":"kim",...}`이라는 그냥 문자열을 → `HelloData` 객체로 조립**하는 거예요.
이걸 어려운 말로 **역직렬화(deserialize)** 라고 합니다. 이제부터 `helloData.getUsername()`처럼 자바 객체답게 쓸 수 있죠.

### ObjectMapper — 이 강의 뒤로도 계속 만날 친구
JSON ↔ 자바 객체를 변환해주는 라이브러리가 **Jackson**이고, 그 핵심 클래스가 `ObjectMapper`입니다.
스프링 부트에 **기본으로 딸려 옵니다.** 방향만 기억하세요:
- `readValue(json, 클래스)` : **JSON → 객체** (읽기, 지금)
- `writeValueAsString(객체)` : **객체 → JSON** (쓰기, 19번에서 만남)

> 📛 **이름 풀이**: `ObjectMapper` = "**객체(Object)를 매핑(Map)해주는 것(-er)**". 왜 `jsonToJava` 같은 이름이 아닐까?
> ① **양방향**이라(JSON↔객체) 한 방향 이름을 못 붙임 — 방향은 `readValue`/`writeValue` 메서드가 담당. ② 클래스는 동작(동사)이 아니라 **정체(명사)** 로 짓는 관례. ③ 사실 **JSON 전용이 아님** — Jackson은 같은 엔진으로 XML(`XmlMapper`)·YAML(`YAMLMapper`)도 처리해서, 형식(json)을 빼고 공통 개념 "객체를 매핑한다"만 이름에 남긴 것.

> 🔗 **4번(싱글톤과 멤버 변수) 복습 문제입니다.** 이 서블릿, `ObjectMapper`를 **멤버 변수**로 두고 있죠?
> (`private ObjectMapper objectMapper = ...`) 4번에서 "멤버 변수는 위험하다"고 그렇게 강조했는데, 이건 왜 괜찮을까요?
> → 정답: `ObjectMapper`는 **한 번 만들면 상태가 변하지 않고(stateless) 스레드 안전(thread-safe)** 하기 때문입니다.
> 4번 표의 "초기화 후 안 바뀌는 객체"에 해당하죠. 오히려 `ObjectMapper`는 생성 비용이 비싸서
> **매 요청마다 new 하지 말고 이렇게 하나 만들어 재사용하는 게 권장**됩니다. — 개념편이 실습에서 이렇게 확인됩니다.

> 💡 그리고 이 JSON 변환은 **서블릿 표준이 아니라는 것**도 짚고 갈게요. 서블릿은 바디를 문자열로 주는 데까지만 해요.
> 문자열 ↔ 객체 변환은 Jackson이라는 **별도 라이브러리**가 하는 겁니다. 실무 스프링에선 이 전 과정(바디 읽기 + 파싱)을
> **`@RequestBody HelloData data`** 한 줄이 통째로 대신해줘요. 그 한 줄 밑에서 지금 이 코드가 돌아간다고 생각하면 됩니다.

## 17. 이제 방향을 뒤집자 — 응답 만들기 (HttpServletResponse, ResponseHeaderServlet)

여기서 강의의 절반이 넘어갑니다. 14~16번은 전부 요청에서 값을 **꺼내는(read)** 쪽이었어요.
지금부터 3개 절(17~19번)은 응답을 **써넣는(write)** 쪽입니다. request와 response는 **거울처럼 대칭**이라,
앞에서 배운 걸 뒤집으면 대부분 이해됩니다.

HTTP 응답 메시지도 요청과 똑같이 세 부분이에요: **① 상태 줄(status-line) ② 헤더(headers) ③ 본문(body).**
`HttpServletResponse`는 이 세 부분을 만드는 도구 상자입니다.

### 코드 — ResponseHeaderServlet
```java
@WebServlet(name = "responseHeaderServlet", urlPatterns = "/response-header")
public class ResponseHeaderServlet extends HttpServlet {

    @Override
    protected void service(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {

        // ① 상태 줄 — 상태 코드
        response.setStatus(HttpServletResponse.SC_OK);   // 200

        // ② 헤더 — 이름/값을 직접 지정
        response.setHeader("Content-Type", "text/plain;charset=utf-8");
        response.setHeader("Cache-Control", "no-cache, no-store, must-revalidate");
        response.setHeader("Pragma", "no-cache");
        response.setHeader("my-header", "hello");   // 내 맘대로 만든 커스텀 헤더도 OK

        // ③ 본문
        PrintWriter writer = response.getWriter();
        writer.println("ok");
    }
}
```

한 줄씩 짚어볼게요.
- `setStatus(HttpServletResponse.SC_OK)` — 상태 코드 200. 여기서 작은 습관 하나. 그냥 `200`이라고 숫자를
  박아도 되지만 `SC_OK`라는 **상수**를 쓰면 코드를 읽는 사람이 "아, OK구나"를 바로 압니다. 302면 `SC_FOUND`, 404면 `SC_NOT_FOUND`.
- `setHeader("이름", "값")` — 응답 헤더를 넣습니다. 재밌는 건 `my-header`처럼 **표준에 없는 헤더도 그냥 만들어 보낼 수 있다**는 거예요.
  헤더는 결국 "이름: 값" 텍스트 한 줄일 뿐이니까요.
- `Cache-Control: no-cache, no-store...` + `Pragma: no-cache` — "이 응답 캐시하지 마"라고 브라우저에 못 박는
  전형적인 조합입니다. 로그인 후 페이지처럼 캐시되면 곤란한 화면에 씁니다.

### 편의 메서드 — "자주 쓰는 헤더는 전용 버튼이 있다"
헤더를 매번 `setHeader("긴 문자열")`로 손으로 조립하면 오타도 나고 번거롭죠. 그래서 서블릿은 자주 쓰는
헤더에 **전용 메서드**를 마련해뒀습니다. 예제에선 아래처럼 주석으로 남겨서 "저수준 vs 편의 메서드"를 비교하게 해놨어요.

```java
// ① Content-Type — setHeader("Content-Type", ...) 대신
response.setContentType("text/plain");
response.setCharacterEncoding("utf-8");   // → Content-Type: text/plain;charset=utf-8 로 합쳐짐

// ② 쿠키 — setHeader("Set-Cookie", ...) 대신
Cookie cookie = new Cookie("myCookie", "good");
cookie.setMaxAge(600);                    // 600초 살아있는 쿠키
response.addCookie(cookie);               // → Set-Cookie: myCookie=good; Max-Age=600

// ③ 리다이렉트 — setStatus(302) + setHeader("Location", ...) 를 한 방에
response.sendRedirect("/basic/hello-form.html");
```

| 하려는 것 | 손으로(setHeader) | 편의 메서드 |
|-----------|------------------|-------------|
| Content-Type | `setHeader("Content-Type","text/plain;charset=utf-8")` | `setContentType()` + `setCharacterEncoding()` |
| 쿠키 심기 | `setHeader("Set-Cookie","myCookie=good; Max-Age=600")` | `new Cookie(...)` + `addCookie()` |
| 리다이렉트 | `setStatus(302)` + `setHeader("Location", ...)` | `sendRedirect("경로")` |

> 💬 오른쪽 편의 메서드는 결국 왼쪽 문자열을 대신 조립해주는 것뿐입니다. 마법이 아니에요.
> 그러니 편의 메서드가 뭘 하는지 헷갈리면, "아 이게 결국 어떤 헤더 문자열이 되는 거지?"를 왼쪽 칸에서 떠올리면 됩니다.
> 그리고 9번 (2)에서 배운 대원칙 — **"응답은 return이 아니라 response에 써넣는 것"** — 은 상태 코드·헤더·본문 전부에 똑같이 적용됩니다.

### 🍪 쿠키 자세히 보기 — "응답에서 쿠키가 하는 역할"

`response.addCookie()`를 보면 헷갈릴 수 있다. **"쿠키는 브라우저가 저장하는 거 아닌가? 왜 서버 응답 코드에 쿠키가 있지?"**
맞다, **저장은 브라우저가 한다.** 서버가 하는 일은 **"이 쿠키 저장해둬"라고 브라우저에게 발급**하는 것이다.

#### 쿠키의 일생 (누가 무엇을 하나)
```
① [서버]    응답에 쿠키를 실어 발급   ← response.addCookie(cookie)
              → 응답 헤더:  Set-Cookie: myCookie=good; Max-Age=600
② [브라우저] 받아서 저장               ← 저장은 브라우저 몫
③ [브라우저] 그 서버로 요청할 때마다 자동으로 붙여 보냄
              → 요청 헤더:  Cookie: myCookie=good
④ [서버]    요청에서 쿠키를 읽음        ← request.getCookies()  (11번 printHeaderUtils 참고)
```
- 즉 **발급·읽기는 서버, 저장·자동전송은 브라우저.** `addCookie()`는 ①번(발급)이다.
- `setMaxAge(600)`도 "600초만 보관하고 지워라"라고 **브라우저의 저장을 지시**하는 값. (안 주면 브라우저 닫을 때까지만 유지되는 세션 쿠키)

#### 쿠키는 왜 필요한가 — HTTP는 무상태(stateless)
HTTP는 요청 하나하나가 독립적이라, 서버는 **다음 요청 때 방금 그 사람을 기억 못 한다.** 그래서 서버가
"이 표식 갖고 다녀"라며 쿠키를 발급하고, 브라우저가 매 요청에 자동으로 붙여 보내면 서버가 "아까 그 사람"임을 안다.
**무상태 HTTP 위에서 신원·상태를 유지하는 장치**가 쿠키다. (놀이공원 손목밴드 비유: 매표소=서버 발급, 방문객=브라우저가 차고 다님)

#### 쿠키는 무조건 서버가 줘야 하나? → 아니다 (생성 2가지 경로)
| 방법 | 누가 | 어떻게 |
|------|------|--------|
| ① 서버 발급 | 서버 | 응답 `Set-Cookie` 헤더 (이 코드) |
| ② 클라이언트 직접 | 브라우저 JS | `document.cookie = "theme=dark; max-age=3600"` |

- **자바스크립트로도 쿠키를 직접 만들 수 있다.** 서버 없이도 가능.
- ⚠️ 단, 서버가 **`HttpOnly`** 옵션으로 발급한 쿠키는 **JS가 읽지도 쓰지도 못한다.** 로그인 세션 쿠키가 XSS로 탈취되는 걸 막는 보안 장치라, 실무에서 인증 쿠키는 보통 `HttpOnly`로 발급한다.

> 💡 **쿠키 vs localStorage/sessionStorage**
> - **쿠키**: 요청마다 서버로 **자동 전송** → 서버와 신원·상태 공유용(로그인 등)
> - **localStorage/sessionStorage**: 순수 브라우저 저장소, **서버로 안 감** → 클라이언트 전용 데이터용

## 18. 응답 본문 ① — HTML 내려주기 (ResponseHtmlServlet)

17번이 상태·헤더였다면, 이제 **본문(body)에 뭘 담느냐**입니다. 첫 번째는 웹의 얼굴, HTML이에요.

### 코드 — ResponseHtmlServlet
```java
@WebServlet(name = "responseHtmlServlet", urlPatterns = "/response-html")
public class ResponseHtmlServlet extends HttpServlet {

    @Override
    protected void service(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {

        response.setContentType("text/html");   // ★ "이건 HTML이야"라고 반드시 선언
        response.setCharacterEncoding("utf-8");

        PrintWriter writer = response.getWriter();
        writer.println("<html>");
        writer.println("<body>");
        writer.println("  <div>안녕?</div>");
        writer.println("</body>");
        writer.println("</html>");
    }
}
```

이 예제의 심장은 딱 한 줄, **`setContentType("text/html")`** 입니다. 9번 (3)에서 이야기한 그 원리가 여기서
실전으로 증명돼요. 이 선언이 있으면 브라우저는 본문을 **웹페이지로 렌더링**해서 "안녕?"이 화면에 뜹니다.
만약 이걸 `text/plain`으로 바꾸면? `<html><body> <div>안녕?</div> ...`가 **태그째로 글자로** 보여요.
같은 본문인데 content-type 한 줄로 결과가 완전히 달라집니다. 꼭 직접 바꿔서 확인해보세요 — 이 대비가 오래 기억에 남습니다.

> ⚠️ 그런데 이 코드, 보면서 뭔가 불편하지 않나요? HTML을 `writer.println("...")`으로 **한 줄 한 줄 문자열로 찍고**
> 있잖아요. 태그가 조금만 길어져도 따옴표와 줄바꿈 지옥이 됩니다. 여기에 사용자 이름 같은 **동적 데이터**까지
> 섞으려면 `"<div>" + name + "</div>"` 식으로 문자열을 이어 붙여야 하고요. 상상만 해도 끔찍하죠.
>
> **바로 이 불편함이 다음 기술을 낳았습니다.** "HTML은 HTML 파일로 예쁘게 써두고, 바뀌는 값만 끼워 넣자" —
> 이게 **JSP·타임리프 같은 템플릿 엔진**의 출발점이에요. 지금 이 불편함을 몸으로 느껴두면, 다음 강의(서블릿 → JSP → MVC 패턴)에서
> "아 그래서 이게 필요했구나"가 확 와닿습니다. **불편을 먼저 겪는 것도 학습의 일부**입니다.

## 19. 응답 본문 ② — API JSON 내려주기 (ResponseJsonServlet)

마지막 예제입니다. 16번에서 **JSON을 읽어 객체로** 만들었죠(들어오는 방향). 이번엔 정확히 그 **반대** —
**객체를 JSON으로 만들어 응답 본문에** 실어 보냅니다(나가는 방향). 요즘 앱·프론트엔드가 서버와 대화하는 가장 흔한 방식이에요.

### 코드 — ResponseJsonServlet
```java
@WebServlet(name = "responseJsonServlet", urlPatterns = "/response-json")
public class ResponseJsonServlet extends HttpServlet {

    private ObjectMapper objectMapper = new ObjectMapper();

    @Override
    protected void service(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {

        response.setContentType("application/json");   // ★ "이건 JSON이야"라고 선언
        response.setCharacterEncoding("utf-8");

        HelloData helloData = new HelloData();          // 보낼 데이터를 객체로 준비
        helloData.setUsername("kim");
        helloData.setAge(20);

        String result = objectMapper.writeValueAsString(helloData);  // 객체 → JSON 문자열
        response.getWriter().write(result);             // {"username":"kim","age":20}
    }
}
```

16번과 나란히 놓고 보면 대칭이 아름답습니다. **같은 `ObjectMapper`인데 방향만 반대로** 씁니다.

| | 16번 (요청 JSON) | 19번 (응답 JSON) |
|---|---|---|
| 방향 | 클라이언트 → 서버 (읽기) | 서버 → 클라이언트 (쓰기) |
| ObjectMapper | `readValue(json, 클래스)` → 객체 | `writeValueAsString(객체)` → JSON |
| content-type | 요청 헤더로 **받는다** | 응답에 내가 **지정한다** (`application/json`) |

이렇게 "읽기(read/deserialize)"와 "쓰기(write/serialize)"가 짝을 이룬다는 걸 잡아두면, 나중에 어떤 라이브러리를
만나도 이 구도로 이해할 수 있어요.

### ⚠️ 실무 감각으로 한 가지 더 — JSON에 붙는 군더더기 charset
```java
response.setContentType("application/json");
response.setCharacterEncoding("utf-8");   // ← 사실 이 줄이 살짝 애매합니다
```
`application/json`은 스펙상 **항상 UTF-8**이라고 이미 정해져 있어요. 그래서 `charset`을 따로 붙이는 건 원래 불필요합니다.
그런데 서블릿에서 `setContentType("application/json")` 다음에 `setCharacterEncoding("utf-8")`을 호출하면,
응답 헤더가 `application/json;charset=utf-8`처럼 **표준에 없는 charset이 덧붙어** 나가요. 동작에는 지장 없지만
"깔끔하지 않다"는 지적을 받을 수 있는 부분입니다. 정석대로 가려면 `setCharacterEncoding`을 빼거나,
`getWriter()` 대신 `getOutputStream()`으로 바이트를 직접 쓰면 됩니다. **지금 단계에선 "이런 디테일이 있다" 정도로만
알아두세요.** 이런 걸 알고 있으면 나중에 코드 리뷰에서 눈에 들어옵니다.

> 💡 실무 스프링 MVC에선 컨트롤러에서 그냥 **객체를 return + `@ResponseBody`** 만 붙이면 이 JSON 변환·응답이
> 자동입니다. 지금 손으로 한 `ObjectMapper` + `response.getWriter()`가 그 밑에서 똑같이 돌아가는 거예요.

## 20. 마무리 — 이 파트 전체를 한 장으로

자, 요청 데이터 받기부터 응답 데이터 내리기까지 쭉 달려왔습니다. 예제가 여러 개라 복잡해 보이지만,
**딱 두 개의 큰 갈래**로 접으면 전부 정리됩니다.

| 상황 | 데이터 위치 | 서블릿 처리 |
|------|-----------|------------|
| **요청** GET 쿼리 파라미터 | URL `?key=value` | `getParameter()` |
| **요청** POST HTML Form | 바디 `key=value` | `getParameter()` — **위와 똑같음** |
| **요청** API 텍스트 | 바디(순수 텍스트) | `getInputStream()` + `StreamUtils` |
| **요청** API JSON | 바디(JSON) | `getInputStream()` → `ObjectMapper.readValue()` |
| **응답** 상태·헤더 | status-line / headers | `setStatus()`, `setHeader()` / 편의 메서드 |
| **응답** HTML | 바디 | `setContentType("text/html")` + `getWriter()` |
| **응답** API JSON | 바디 | `setContentType("application/json")` + `writeValueAsString()` |

**요청에서 값 꺼내는 법, 이 두 갈래만 기억하세요.**
1. **`key=value` 파라미터** → 출처(URL이든 폼 바디든) 상관없이 무조건 **`getParameter()`**.
2. **바디에 담긴 덩어리(텍스트·JSON)** → **`getInputStream()`** 으로 직접 읽고, JSON이면 **`ObjectMapper`** 로 객체 변환.

> 📌 **혼동 포인트 짚고 넘어가기** (자세한 건 15번 심화 참고)
> - **"POST Form도 바디에 있는데 왜 `getParameter()`지?"** → form은 `getInputStream()`으로도 읽을 수 있지만(`username=hello&age=20` 날것으로 나와 직접 파싱해야 함),
>   톰캣이 **`application/x-www-form-urlencoded`만 자동 파싱**해주기 때문에 `getParameter()`가 편하게 되는 것. 텍스트·JSON은 자동 파싱을 안 해줘서 `getParameter()`가 안 됨. → **차이를 가르는 건 content-type.**
> - **`getParameter()`와 `getInputStream()`은 한 요청에서 같이 못 씀** — 바디는 한 번 읽으면 비워지므로, 먼저 읽은 쪽이 이기고 나중 쪽은 빈 값/null.

그리고 마지막으로 강의를 시작할 때(1부 7번의 계층 그림) 했던 약속을 다시 지킬 차례입니다.
지금 우리가 손으로 짠 이 모든 저수준 코드 — `getParameter`, `getInputStream`, `ObjectMapper`, `response.getWriter()` —
는 실무 스프링 MVC에서 이렇게 **단 한 줄씩으로 사라집니다.**

| 우리가 직접 한 것 (서블릿) | 스프링 MVC에서는 |
|---|---|
| `request.getParameter("username")` | `@RequestParam String username` |
| `getInputStream()` + `ObjectMapper.readValue()` | `@RequestBody HelloData data` |
| `setContentType("application/json")` + `writeValueAsString()` + `getWriter()` | 객체 return + `@ResponseBody` |

**"그럼 스프링만 배우면 되지, 왜 이 고생을 했나?"** 그 답이 이 파트의 결론입니다. 저 한 줄짜리 애노테이션 밑에서
**실제로 무슨 일이 벌어지는지**를 이제 우리는 압니다. 값이 null로 올 때, 한글이 깨질 때, JSON 파싱이 실패할 때 —
남들은 "왜 안 되지?" 하고 막힐 때 우리는 밑바닥 그림을 그릴 수 있어요. **편리함의 정체를 알고 쓰는 것과 모르고 쓰는 것의 차이**,
그걸 위해 서블릿을 직접 만져본 겁니다.

# 부록. 애노테이션이 자바 것인지 스프링 것인지 구분법

**가장 확실한 방법: `import`의 패키지 경로를 본다.**

| 패키지 시작 | 출신 | 예시 |
|------------|------|------|
| `java.*` | 자바 언어 기본 | `@Override`, `@Deprecated` |
| `javax.*` / `jakarta.*` | 자바 표준(확장) | `@WebServlet`, `@Entity`, `@PostConstruct` |
| `org.springframework.*` | 스프링 | `@Controller`, `@Autowired`, `@RequestMapping` |

- IDE에서 애노테이션에 커서 두고 `Ctrl + B` → 원본 소스로 이동해 패키지 확인
- 이름 중복 주의: `@Transactional`은 스프링 것과 JPA 표준 것이 둘 다 있음 → 반드시 패키지 확인

### java / javax / jakarta 차이
- `java.*` : 자바의 **핵심 라이브러리** (String, List 등, 항상 존재)
- `javax.*` : 나중에 붙은 **확장 기능** (서블릿, JPA 등). 이름은 확장이지만 사실상 자바 표준
- `jakarta.*` : **`javax`와 같은 것, 이름만 바뀜**. Java EE가 오라클→이클립스 재단으로 이관되며
  상표 문제로 `javax` → `jakarta`로 변경됨
- 실무 기준: **스프링 부트 2.x = `javax`, 3.x = `jakarta`**
  (이 프로젝트는 `import javax.servlet...`을 쓰므로 **2.x 기반**)
