# 서블릿(Servlet) 학습 정리

> **이 문서의 목표**
> "서블릿이 무엇인지"를 개념부터 이해하고, 그 위에서 **우리가 실습으로 직접 짠 코드**가
> 왜 그렇게 생겼는지 파악한다.
>
> **미리 알아둘 것**: 실무(스프링 MVC)에서는 서블릿을 직접 만들 일이 거의 없다.
> 스프링이 `DispatcherServlet`이라는 서블릿을 이미 다 만들어두었기 때문이다.
> **여기서 서블릿을 직접 만들어 보는 이유는, 스프링 아래에서 실제로 무엇이 돌아가는지
> 그 "밑바닥 원리"를 이해하기 위한 학습 목적**이다. (2부의 코드는 전부 그런 학습용 코드다.)

---

# 1부. 개념편 — 서블릿이란 무엇인가

## 1. 서블릿(Servlet)이란?

**웹 요청(request)을 받아 처리하고, 응답(response)을 만들어 돌려주는 "프로그램 단위"** 이다.

브라우저가 서버에 요청을 보내면, 그 요청을 실제로 처리하는 자바 객체가 서블릿이다.
개념적으로 서블릿은 다음 역할만 담당한다.

```
요청이 들어온다 → (서블릿) 요청을 처리한다 → 응답을 만든다
```

핵심 성질:
- 서블릿의 **동작 방식·생명주기(언제 만들어지고 실행되고 사라지는지)는 이미 표준으로 정해져** 있다.
- 개발자는 그 틀 안에서 **"요청 하나를 어떻게 처리할지"라는 실제 로직만** 채운다.
- 즉 서블릿을 쓴다는 것은 **바퀴를 다시 발명하지 않고, 이미 정해진 규격 위에 로직만 얹는 것**이다.

> 자바에서 서블릿은 `HttpServlet` 클래스를 상속해서 만든다.
> `HttpServlet`을 상속받는 순간 그 클래스는 "하나의 서블릿"이 된다. (구체적인 코드는 2부에서)

---

## 2. 서블릿이 없다면? (서블릿이 편리한 이유)

브라우저가 요청 하나를 보냈을 때, 서블릿이 없다면 개발자가 이 모든 걸 직접 해야 한다.

| 해야 할 일 | 서블릿 없이 | 서블릿(WAS) 쓰면 |
|-----------|:---:|:---:|
| ① TCP 소켓 열기 / 연결 대기 | 직접 😫 | WAS가 대신 ✅ |
| ② 들어온 바이트 읽기 | 직접 😫 | WAS가 대신 ✅ |
| ③ HTTP 파싱 (경로/파라미터/헤더/본문/인코딩) | 직접 😫😫😫 | `request` 객체로 ✅ |
| ④ 라우팅 (어느 로직 실행할지) | if문 직접 | 매핑 자동 ✅ |
| ⑤ HTTP 응답 조립 (상태줄/헤더/본문) | 직접 😫 | `response` 객체로 ✅ |
| ⑥ 멀티스레드 관리 | 직접 😫😫 | WAS가 대신 ✅ |
| **내 비즈니스 로직** | 직접 | **직접 (이것만!)** |

→ 서블릿(WAS)은 **HTTP·네트워크·스레드라는 반복적이고 어려운 뼈대를 전부 대신 처리**해줘서,
개발자가 **`request`에서 값 꺼내기 → 로직 처리 → `response`에 쓰기**, 핵심에만 집중하게 해준다.

---

## 3. 서블릿 컨테이너 (WAS, 예: 톰캣)

**서블릿을 대신 실행하고 관리해주는 서버 프로그램.** 대표적으로 톰캣(Tomcat).

서블릿은 그냥 클래스일 뿐 혼자서는 아무것도 못 한다. 요청이 오면 컨테이너가:

1. 요청을 받는다 (네트워크/소켓 처리)
2. HTTP 메시지를 파싱해 `HttpServletRequest`를 만든다
3. 빈 `HttpServletResponse`를 만든다
4. URL에 매핑된 서블릿을 찾는다
5. 그 서블릿을 호출한다 ← **여기서 개발자가 짠 로직이 실행됨**
6. 응답 객체를 HTTP 메시지로 바꿔 브라우저에 보낸다

5번(내 로직)을 제외한 전부를 컨테이너가 대신 해준다.
또한 서블릿 객체를 개발자가 직접 `new` 하지 않는다 — **컨테이너가 만들고 생명주기를 관리**한다.

```
브라우저 ⇅ HTTP ⇅ 서블릿 컨테이너(톰캣) → 서블릿 / 또는 스프링의 DispatcherServlet
```

> 스프링 부트는 이 톰캣이 프로젝트 안에 **내장(embedded)** 되어 있어, 따로 설치 없이 main() 실행 시 함께 켜진다.

---

## 4. 서블릿은 싱글톤

톰캣은 서블릿을 요청마다 새로 만들지 않고, **처음에 딱 1개만 만들어 모든 요청이 공유**한다.

**이유**
- 요청마다 `new` 하면 낭비 → 하나 만들어 재사용하는 게 효율적 (성능/자원)
- 사용자별 데이터(예: `username=kim`)는 요청마다 새로 만들어지는 `request` 객체에 담기므로,
  서블릿 객체 자체는 공유해도 문제가 없다.

### ⚠️ 주의: 멤버 변수(공유 상태) 조심

여러 스레드가 같은 서블릿 1개를 동시에 실행하므로, **요청마다 값이 바뀌는 데이터를 멤버 변수에 담으면 안 된다.**

```java
private String username;   // ❌ 위험! 여러 스레드가 동시에 덮어써서 데이터가 섞임
```

- 컴파일 에러가 아니라, **동시 접속 시에만 조용히 데이터가 섞이는 버그(동시성 버그)** → 더 위험
- kim이 요청했는데 lee의 데이터를 받는 식의 사고 발생 가능
- 해결: 요청 관련 데이터는 **메서드 안의 지역 변수**로 둔다 (지역 변수는 스레드마다 독립)

| 멤버 변수 종류 | 안전? | 예시 |
|---|:---:|---|
| 요청마다 바뀌는 데이터 | ❌ | `username`, `count`, 로그인 사용자 |
| 초기화 후 안 바뀌는 상수/설정 | ✅ | `final String greeting` |
| 주입받은 stateless 객체 | ✅ | `memberService`, `repository` |

> 스프링 빈(`@Controller`, `@Service`)도 기본이 싱글톤이라 같은 원리·주의점이 적용된다.

## 5. 서블릿은 어떻게 동시 요청을 처리하나 (멀티스레드)

**연결고리**: 4번에서 "서블릿은 싱글톤(딱 1개)"이라고 했다. 그런데 사용자가 동시에 수백 명 들어오면,
그 1개짜리 서블릿이 어떻게 여러 요청을 동시에 처리할까? → **서블릿 컨테이너(톰캣)가 서블릿을
"멀티스레드"로 실행**하기 때문이다. 이게 4번의 "멤버 변수 주의"가 나온 근본 이유이기도 하다.

- 스레드 = 코드를 실행하는 "일꾼" 하나
- **톰캣은 요청마다 스레드를 하나씩 배정**해서, 그 스레드가 서블릿의 처리 메서드를 실행한다
  (싱글 스레드면 요청들이 서로 막혀서 하나 끝날 때까지 대기)
- 이 여러 스레드가 **같은 싱글톤 서블릿 1개**를 동시에 실행 → 그래서 멤버 변수 주의(4번)
- 즉 **"서블릿 하나 + 요청마다 스레드"** 구조. 서블릿을 이해하면 이 멀티스레드 얘기가 딸려 나온다.

### 스레드 풀 (Thread Pool)
스레드도 매번 만들면 비싸고, 폭주 시 서버가 죽는다. 그래서:
- 스레드를 미리 여러 개 만들어 풀에 대기
- 요청 오면 꺼내 쓰고, 끝나면 버리지 않고 풀에 반납(재사용)
- 개수 상한이 있어 폭주해도 서버 보호 (톰캣 기본 최대 200)

**이 모든 스레드 관리(생성/배정/반납)는 WAS가 대신 해준다. 개발자는 "요청 하나 처리 로직"만 짜면 된다.**
단, 그 로직을 스레드 안전하게 짜는 것(멤버 변수 주의)은 개발자 몫이다.

### 스레드 개수 설정
스레드 관리 "코드"는 안 짜지만, 개수 등 "설정값"은 개발자가 정할 수 있다.

```properties
# application.properties (스프링 부트 내장 톰캣)
server.tomcat.threads.max=200
server.tomcat.threads.min-spare=10
server.tomcat.max-connections=8192
server.tomcat.accept-count=100
```

### 적정 스레드 수 기준
- **CPU 바운드**(계산 위주): 스레드 ≈ 코어 수
- **I/O 바운드**(DB/API 대기 많음 = 웹 대부분): 코어 수보다 훨씬 많이 (대기 시간에 다른 스레드가 CPU 사용)
- 근사 공식: `코어 수 × (1 + 대기시간/작업시간)`
- **실제로는 부하 테스트(JMeter, nGrinder, k6)로 측정해 결정**. 이론값은 참고.

> **컨텍스트 스위칭 비용**: CPU가 실행 스레드를 바꿀 때 ① 이전 스레드 상태 저장/복원 ② CPU 캐시가 식어
> 느린 메모리 재접근이 발생. 그래서 스레드가 너무 많으면 오히려 느려진다.

## 6. 서블릿 애플리케이션의 배포 형태 (WAR vs JAR)

**연결고리**: 우리가 만든 서블릿은 3번에서 봤듯 **서블릿 컨테이너(톰캣) 위에서만** 돌아간다.
그럼 "내가 만든 서블릿들을 어떻게 묶어서 톰캣에 올려 실행하나?" → 이 **패키징(묶음) 형태**가 WAR/JAR이다.
특히 **WAR는 원래 서블릿/웹앱을 톰캣에 배포하기 위해 만들어진 전용 포맷**이라 서블릿과 직접 관련된다.

| 항목 | JAR | WAR |
|------|-----|-----|
| 뜻 | Java Archive | Web Application Archive |
| 용도 | 범용 자바 코드/라이브러리 | 웹 애플리케이션 전용 |
| 구조 | 자유 | `WEB-INF/` 등 정해진 구조 |
| 실행 | `java -jar`로 **단독 실행** | **WAS(톰캣)에 배포**해야 실행 |
| 톰캣 | (스프링 부트는) **내장** | 외부에 별도 설치 |
| 요즘 추세 | ✅ 주류 (스프링 부트) | 전통적/특수 상황 |

## 7. 우리가 배운 서블릿이 스프링에서 어떻게 쓰이나 (서블릿 vs 스프링 MVC)

**연결고리**: "그럼 실무에서 쓰는 스프링 MVC는 서블릿이랑 무슨 관계지?"에 대한 답이다.
결론부터: **스프링 MVC도 결국 서블릿 위에서 돈다.** 우리가 지금 배우는 서블릿이 바로 그 토대다.

"더 크다/작다"가 아니라 **계층(누가 누구 위에서 도는가)** 관계다.

```
┌─────────────────────────────────┐
│  스프링 MVC (@Controller, ...)    │  ← 서블릿 위에 지은 편의 기능
├─────────────────────────────────┤
│  서블릿 (HttpServlet, service)    │  ← 근본 토대 (자바 웹 표준)
├─────────────────────────────────┤
│  서블릿 컨테이너 (톰캣)            │  ← 실행·관리
└─────────────────────────────────┘
```

- **서블릿** = 자바 웹의 근본 토대(표준). 더 아래(기반)에 있다.
- **스프링 MVC** = 그 서블릿 위에 편의 기능을 잔뜩 얹은 프레임워크. 기능은 더 풍부.
- 스프링 MVC의 심장 **`DispatcherServlet`도 결국 `HttpServlet`을 상속한 서블릿**이다.
  (상속: `HttpServlet` → `HttpServletBean` → `FrameworkServlet` → `DispatcherServlet`)
- `DispatcherServlet`은 **모든 요청을 혼자 받아 알맞은 `@Controller`로 분배**하는 프론트 컨트롤러.

> 스프링 MVC를 "쓴다" = MVC라는 개념(패턴)을 스프링 팀이 구현해 배포한 **라이브러리**를
> 프로젝트에 의존성으로 추가해 가져다 쓴다는 뜻. (개념만 빌리는 게 아니라 실제 코드를 다운받아 씀)
>
> **다시 강조**: 그래서 실무에서는 서블릿을 직접 안 만든다. 2부의 코드는 이 토대를
> 눈으로 확인하기 위한 학습용이다.

# 2부. 실습 코드편 — 우리가 직접 만든 학습용 코드

> ⚠️ 아래 코드는 **스프링이 대신 해주는 밑바닥을 직접 체험하려고 만든 학습용 코드**다.
> 실무에서는 이렇게 `@WebServlet` + `service()`를 직접 짜지 않고, `@Controller`로 처리한다.

## 8. 왜 `@ServletComponentScan`을 붙였나?

```java
@ServletComponentScan   // 서블릿 자동 등록
@SpringBootApplication
public class ServletApplication {
    public static void main(String[] args) {
        SpringApplication.run(ServletApplication.class, args);
    }
}
```

### 두 종류의 애노테이션을 구분해야 한다

| | 애노테이션 | 누가 등록? | @ServletComponentScan 필요? |
|---|-----------|-----------|:---:|
| **스프링 빈** | `@Controller`, `@Service`, `@Component` | `@SpringBootApplication`이 자동 스캔 | ❌ |
| **표준 서블릿** | `@WebServlet`, `@WebFilter`, `@WebListener` | 기본으로는 스캔 안 함 | ✅ **필요** |

### 이유
- 스프링에 내장된 건 **`DispatcherServlet`** 이다. (자동 등록됨)
- 하지만 우리가 만들 `@WebServlet`은 **스프링 게 아니라 자바 서블릿 표준(javax.servlet)** 애노테이션이다.
- 전통적 외부 톰캣은 `@WebServlet`을 스캔해줬지만, **스프링 부트의 내장 톰캣은 기본적으로 스캔하지 않는다.**
- 그냥 두면 `@WebServlet("/hello")`를 붙여도 무시되어 `/hello`가 404.
- 그래서 `@ServletComponentScan`으로 **"@WebServlet/@WebFilter/@WebListener도 스캔해서 등록해줘"** 라고 켜준다.

→ `@Controller` 같은 스프링 자체 애노테이션엔 불필요하고, **우리처럼 순수 서블릿(`@WebServlet`)을 실습할 때만** 필요하다.

---

## 9. HelloServlet 코드 — 우리가 만든 학습용 서블릿

```java
@WebServlet(name = "helloServlet", urlPatterns = "/hello")
public class HelloServlet extends HttpServlet {

    @Override
    protected void service(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {

        System.out.println("HelloServlet.service");
        System.out.println("request = " + request);
        System.out.println("response = " + response);

        String username = request.getParameter("username");
        System.out.println("username = " + username);

        response.setContentType("text/plain");
        response.setCharacterEncoding("utf-8");
        response.getWriter().write("hello " + username);
    }
}
```

- `extends HttpServlet` → 이 클래스가 하나의 서블릿이 된다. (개념편 1번의 실제 구현)
- `@WebServlet(urlPatterns = "/hello")` → 이 서블릿을 `/hello` 주소에 매핑(등록). 8번의 `@ServletComponentScan`이 있어야 실제 등록됨.

### 참고: 왜 `doGet`이 아니라 `service()`를 오버라이드했나? (학습용 선택)

원래 `HttpServlet`의 `service()`는 HTTP 메서드(GET/POST)를 보고 알맞은 `doGet`/`doPost`로 나눠주는
**"교통정리 담당"** 으로 이미 구현되어 있다.

| 계층 | 메서드 | 구현 주체 |
|------|--------|-----------|
| 최상위 관문 | `service()` (Servlet 인터페이스) | 이미 구현됨 |
| HTTP 분기 | `service()` (HttpServlet) | **이미 구현됨** ← GET/POST 나눠줌 |
| 실제 처리 | `doGet()`, `doPost()` | 원래는 여기를 구현 |

그런데 이 코드는 부모 `service()`를 **통째로 덮어썼다**(`super.service()`도 호출 안 함).
- 그래서 GET/POST 분기가 사라지고, 메서드 상관없이 무조건 이 `service()` 하나로 들어온다.
- `doGet`, `doPost`는 호출되지 않는다.
- **의도된 학습용 선택**: "서블릿의 진짜 관문은 service()다"라는 동작 원리를 보여주려는 것.
  (실무/일반적으로는 `service()`가 아니라 `doGet`/`doPost`를 오버라이드한다.)

## 10. 코드 한 줄씩 상세 분석

### (1) HttpServletRequest를 어떻게 사용할 수 있나?

- 코드 어디에도 `new HttpServletRequest()`가 없다. **톰캣이 만들어서 매개변수로 넣어준다.** (개념편 3번)
- 흐름: `브라우저 요청 → 톰캣이 HTTP 파싱 → RequestFacade 객체 생성 → service(여기에 전달)`
- 우리는 받아서 **정보를 꺼내 쓰기만** 하면 된다.
  ```java
  request.getParameter("username");  // ?username=kim → "kim"
  request.getMethod();               // GET/POST
  request.getHeader("User-Agent");   // 헤더
  request.getRequestURI();           // 경로
  ```
- 실제 객체는 톰캣의 `RequestFacade`지만, 우리는 `HttpServletRequest`라는 **인터페이스(규격)** 로 받는다.
  → 톰캣이든 다른 WAS든 코드가 안 바뀐다.

> 실행 로그로 확인됨:
> `request = org.apache.catalina.connector.RequestFacade@74bea4a0`
> - `org.apache.catalina...` = 톰캣(Catalina)이 만든 클래스
> - `RequestFacade` = HttpServletRequest 인터페이스의 실제 구현체
> - `@74bea4a0` = 객체 식별용 해시코드 (의미 없음, 무시)
> - **Facade** = 톰캣 내부의 복잡한 진짜 객체를 감추고, 안전한 메서드만 열어주는 "껍데기" 패턴

### (2) return이 없는데 어떻게 응답이 클라이언트로 날아가나?

**핵심: 응답은 return으로 돌려주는 게 아니라, response 객체에 "써넣는" 방식이다.**

```
① 톰캣이 "빈 response 객체"를 만들어 service()에 넣어줌 (빈 답안지)
② 나는 response에 내용을 써넣음
   - setContentType / setCharacterEncoding → 헤더 기록
   - getWriter().write(...)                → 본문 기록
③ service() 메서드가 끝남 (return 없어도 메서드 끝나면 종료)
④ 톰캣이 그 response를 보고 HTTP 응답 메시지로 조립 → 브라우저로 전송
```

- 내가 응답을 "보내는" 게 아니라, response에 **채워만 놓으면 톰캣이 대신 보낸다.**
- 그래서 `service()`는 `void`여도 되고, `return`이 없어도 응답이 나간다 (데이터는 이미 response 안에 있음).
- 비유: 회사가 준 양식(response)에 내용만 채워 제출하면 발송은 회사(톰캣)가 대신.

> 스프링 MVC의 `@Controller`는 `return "뷰이름"`을 쓰지만, 그 내부에서도 결국 이 response에
> 써넣는 작업이 일어난다. 밑바닥 원리는 동일.

### (3) Content-Type: `text/plain` — 앞/뒤 의미

```java
response.setContentType("text/plain");
```

- 응답 본문이 **어떤 종류의 데이터인지** 브라우저에 알려주는 값 (= MIME 타입)
- 형식: `타입/서브타입`
  - 앞(`text`) = 대분류 ("텍스트 계열이야")
  - 뒤(`plain`) = 세부 종류 ("서식 없는 순수 텍스트야")

| Content-Type | 의미 |
|--------------|------|
| `text/plain` | 순수 텍스트 (글자 그대로 표시) |
| `text/html` | HTML 문서 (브라우저가 웹페이지로 렌더링) |
| `application/json` | JSON 데이터 |
| `image/png` | PNG 이미지 |

- **왜 지정?** 브라우저는 Content-Type을 보고 처리 방식을 결정한다.
  같은 `<h1>hi</h1>`도 `text/plain`이면 태그까지 글자로 보이고, `text/html`이면 큰 제목으로 렌더링된다.

### (4) 인코딩 / UTF-8 / 왜 지정하나

```java
response.setCharacterEncoding("utf-8");
```

**인코딩이란?**
- 컴퓨터는 글자를 모르고 숫자(0/1)만 안다. 그래서 **글자 → 숫자(바이트)로 바꾸는 규칙**이 인코딩.
- 규칙이 여러 종류라, 같은 글자도 규칙마다 다른 숫자가 된다.
  - `'가'` → UTF-8: `234 176 128` / EUC-KR: `176 161`

**왜 지정하나? (글자 깨짐 방지)**
- 보내는 쪽(서버)과 받는 쪽(브라우저)이 **같은 규칙**을 써야 글자가 복원된다.
- 규칙 불일치 = 한글 깨짐(`ê°€`, `?????`, `�`)의 원인.
- `setCharacterEncoding("utf-8")` = "나는 UTF-8로 글자를 숫자로 바꿔 보낼게, 너도 UTF-8로 읽어".

**UTF-8이란?**
- 전 세계 모든 문자(한글/영어/한자/이모지)를 표현하는 인코딩 규칙.
- 웹 표준이자 사실상 기본값. 영어 1바이트, 한글 3바이트 식으로 필요한 만큼 사용(효율적).
- 특별한 이유 없으면 **무조건 UTF-8**이 정답.

**둘의 관계**
```java
response.setContentType("text/plain");   // 데이터 종류
response.setCharacterEncoding("utf-8");  // 글자 인코딩
```
→ 실제 응답 헤더: `Content-Type: text/plain;charset=utf-8`
(`response.setContentType("text/plain;charset=utf-8")`로 한 줄로 합쳐 쓰기도 함)

### (5) 한눈 정리

| 코드 | 하는 일 |
|------|---------|
| `HttpServletRequest request` | 톰캣이 만들어 넣어준 요청 정보 객체 (내가 new 안 함) |
| `request.getParameter("username")` | `?username=kim`에서 `kim` 꺼내기 |
| `HttpServletResponse response` | 톰캣이 만들어 넣어준 빈 응답 객체 (여기에 채워 넣음) |
| `response.setContentType("text/plain")` | "본문은 순수 텍스트" (타입/서브타입) |
| `response.setCharacterEncoding("utf-8")` | "글자는 UTF-8 인코딩" (깨짐 방지) |
| `response.getWriter().write(...)` | 응답 본문에 내용 써넣기 |
| **return 없음** | response에 채워두면 톰캣이 알아서 HTTP 응답으로 조립·전송 |

## 11. RequestHeaderServlet — HTTP 요청 정보 전체 조회

> `HelloServlet`에서는 `request.getParameter()` 하나만 썼다. 이번엔 **`request` 객체가 제공하는
> 다양한 조회 메서드**로, HTTP 요청 안에 담긴 정보(시작 줄·헤더·연결 정보)를 전부 꺼내보는 실습이다.

### 예제가 의미하는 것
브라우저가 `http://localhost:8080/request-header`로 접속하면, 이 서블릿은 요청에 담긴 모든 정보를
**콘솔에 출력**한다. (응답 화면은 비어 있고, 결과는 IntelliJ 하단 콘솔에서 확인)
→ "요청(request) 안에는 대체 뭐가 들어있나?"를 눈으로 보는 게 목적.

### 먼저: HTTP 요청 메시지의 구조
```
GET /request-header?username=kim HTTP/1.1     ← ① 시작 줄 (start-line)
Host: localhost:8080                          ┐
User-Agent: Mozilla/5.0                       │ ② 헤더 (headers)
Accept-Language: ko-KR,ko;q=0.9               │
Cookie: sessionId=abc123                      ┘
                                              ← 빈 줄 (헤더 끝)
{ "name": "kim" }                             ← ③ 본문 (body, POST 등)
```
톰캣이 이 메시지를 파싱해 `request` 객체에 담아주므로, 우리는 메서드만 호출하면 된다.

### 코드 구조
```java
protected void service(...) {
    printStartLine(request);    // ① 시작 줄 조회
    printHeaders(request);      // ② 모든 헤더 조회
    printHeaderUtils(request);  // ② 자주 쓰는 헤더 "편의 조회"
    printEtc(request);          // 기타(연결 정보) 조회
}
```

### ① printStartLine — 시작 줄 정보
```java
request.getMethod()       // GET, POST 등 HTTP 메서드
request.getProtocol()     // HTTP/1.1
request.getScheme()       // http / https
request.getRequestURL()   // http://localhost:8080/request-header (호스트 포함 전체 주소)
request.getRequestURI()   // /request-header (경로만)
request.getQueryString()  // username=kim (? 뒤의 쿼리)
request.isSecure()        // https 여부
```
- **URL vs URI**: `getRequestURL()`=전체 주소, `getRequestURI()`=경로만, 쿼리는 `getQueryString()`으로 따로.

### ② printHeaders — 모든 헤더 반복 조회
```java
request.getHeaderNames().asIterator()
        .forEachRemaining(headerName -> System.out.println(headerName + ": " + request.getHeader(headerName)));
```
- `getHeaderNames()` → 요청에 온 **모든 헤더 이름 목록** 반환 (구식 타입인 `Enumeration`)
- `.asIterator()` (자바 9+) → 요즘 스타일로 순회할 수 있게 변환 → `forEachRemaining`으로 하나씩 출력
- `getHeader(headerName)` → 그 이름에 해당하는 **헤더 값**을 조회
  - 즉 `getHeaderNames()`(이름 목록)로 돌면서, 각 이름을 `getHeader()`에 넣어 값을 꺼내 `이름: 값`으로 출력

**출력 예시**
```
host: localhost:8080
connection: keep-alive
user-agent: Mozilla/5.0 ...
accept-language: ko-KR,ko;q=0.9,en-US;q=0.8
```

> 💡 흔한 실수: 뒤쪽에 값 대신 `headerName`을 또 쓰면 `host: host`처럼 **이름만 두 번** 나온다.
> 값을 보려면 반드시 `request.getHeader(headerName)`로 값을 조회해야 한다.

### ③ printHeaderUtils — 자주 쓰는 헤더 편의 조회
헤더를 매번 `getHeader("이름")`으로 꺼내면 번거로우니, 서블릿이 자주 쓰는 것들에 **전용 메서드**를 제공한다.
```java
request.getServerName() / getServerPort()   // Host 헤더 → 서버 이름/포트
request.getLocales() / getLocale()          // Accept-Language 헤더 → 선호 언어(우선순위/1순위)
request.getCookies()                        // Cookie 헤더 → Cookie[] (null 체크 필수!)
request.getContentType() / getContentLength() / getCharacterEncoding()  // 본문 관련
```
- 이것들도 결국 다 헤더다. `getServerName()`은 `Host` 헤더를 파싱해주는 것뿐. 직접 `getHeader("Host")` 해도 되지만 편의 메서드가 더 안전.
- `getCookies()`는 쿠키가 없으면 `null` → 그냥 for로 돌리면 NPE. 그래서 `if (... != null)`로 감쌌다.

### ④ printEtc — 기타(네트워크 연결 정보)
HTTP 메시지 내용이 아니라, **누가 어디서 접속했는지(TCP 연결 정보)**.
```java
// Remote = 요청 보낸 쪽 (클라이언트)
request.getRemoteHost() / getRemoteAddr() / getRemotePort()
// Local = 요청 받은 쪽 (내 서버)
request.getLocalName() / getLocalAddr() / getLocalPort()
```
- **Remote = 상대방(클라이언트), Local = 나(서버)** 로 기억하면 안 헷갈림.

### 사용된 개념 정리
| 개념 | 설명 |
|------|------|
| HTTP 요청 구조 | 시작 줄 / 헤더 / 본문 3부분 |
| `request` 조회 메서드 | 톰캣이 파싱해 담아둔 요청 정보를 꺼내는 다양한 메서드 |
| `Enumeration` + `asIterator()` | 구식 컬렉션(Enumeration)을 자바 9+ 스타일로 순회 |
| 편의 메서드 | 자주 쓰는 헤더(Host, Language, Cookie, Content)를 전용 메서드로 제공 |
| null 체크 | `getCookies()`는 null 가능 → NPE 방지 |
| Remote vs Local | 클라이언트 정보 vs 서버 정보 |

## 12. IntelliJ 메서드 추출 단축키 (Extract Method)

`printStartLine`, `printHeaders` 같은 메서드들은 **원래 `service()` 안에 한 덩어리로 들어있던 코드**였다.
그걸 **"메서드 추출(Extract Method)"** 기능으로 각각의 메서드로 분리한 것이다.

### 무엇인가
길고 복잡한 코드 블록을 **드래그로 선택 → 단축키 → 별도 메서드로 자동 분리**해주는 리팩터링 기능.
- 선택한 코드가 새 메서드로 빠지고
- 원래 자리에는 그 메서드 **호출문**이 자동으로 들어가며
- 필요한 변수(예: `request`)는 **매개변수로 자동 전달**된다

### 단축키
| OS | 단축키 |
|----|--------|
| **Windows / Linux** | `Ctrl + Alt + M` |
| **macOS** | `Cmd + Option + M` |

### 사용법
1. 메서드로 빼고 싶은 코드 줄들을 **드래그로 선택**
2. 단축키를 누름 → **Windows/Linux: `Ctrl + Alt + M`** / **macOS: `Cmd + Option + M`**
3. 뜨는 창에서 **메서드 이름 입력**(예: `printStartLine`) → Enter
4. 끝. 코드가 새 메서드로 분리되고 원래 자리엔 호출문이 생김

### 왜 쓰나
- `service()`가 수십 줄로 길어지면 읽기 어렵다 → **역할 단위로 쪼개면** 한눈에 흐름이 보인다
  (`service()`만 보면 "시작줄 → 헤더 → 편의조회 → 기타" 순서가 딱 드러남)
- 코드 중복 제거, 재사용에도 유용

> **함께 알아두면 좋은 리팩터링 단축키 (IntelliJ)**
> | 기능 | Windows / Linux | macOS | 설명 |
> |------|-----------------|-------|------|
> | 메서드 추출 | `Ctrl + Alt + M` | `Cmd + Option + M` | 코드 → 메서드로 분리 |
> | 변수 추출 | `Ctrl + Alt + V` | `Cmd + Option + V` | 값/식 → 변수로 분리 |
> | 이름 바꾸기 | `Shift + F6` | `Shift + F6` | 변수/메서드명 일괄 변경(참조까지 자동) |
> | 인라인(추출 반대) | `Ctrl + Alt + N` | `Cmd + Option + N` | 메서드/변수를 원래 자리로 되돌림 |
> | 리팩터링 메뉴 전체 | `Ctrl + Alt + Shift + T` | `Ctrl + T` | 가능한 리팩터링 목록 표시 |

# 부록. 애노테이션이 자바 것인지 스프링 것인지 구분법

**가장 확실한 방법: `import`의 패키지 경로를 본다.**

| 패키지 시작 | 출신 | 예시 |
|------------|------|------|
| `java.*` | 자바 언어 기본 | `@Override`, `@Deprecated` |
| `javax.*` / `jakarta.*` | 자바 표준(확장) | `@WebServlet`, `@Entity`, `@PostConstruct` |
| `org.springframework.*` | 스프링 | `@Controller`, `@Autowired`, `@RequestMapping` |

- IDE에서 애노테이션에 커서 두고 `Ctrl + B` → 원본 소스로 이동해 패키지 확인
- 이름 중복 주의: `@Transactional`은 스프링 것과 JPA 표준 것이 둘 다 있음 → 반드시 패키지 확인

### java / javax / jakarta 차이
- `java.*` : 자바의 **핵심 라이브러리** (String, List 등, 항상 존재)
- `javax.*` : 나중에 붙은 **확장 기능** (서블릿, JPA 등). 이름은 확장이지만 사실상 자바 표준
- `jakarta.*` : **`javax`와 같은 것, 이름만 바뀜**. Java EE가 오라클→이클립스 재단으로 이관되며
  상표 문제로 `javax` → `jakarta`로 변경됨
- 실무 기준: **스프링 부트 2.x = `javax`, 3.x = `jakarta`**
  (이 프로젝트는 `import javax.servlet...`을 쓰므로 **2.x 기반**)
